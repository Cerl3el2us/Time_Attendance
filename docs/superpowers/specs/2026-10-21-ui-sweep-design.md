# กวาดหน้าตาทั้งแอป 3 แกน: โหมดมืด × ความกว้างหน้าจอ × การล้นขอบ

เอกสารออกแบบ · 2026-10-21 · **ยังไม่ได้รับอนุมัติ — ห้ามลงมือแก้ตามเอกสารนี้จนกว่าเจ้าของจะอนุมัติ**

## ที่มา

เจ้าของรายงานมา 3 เรื่องในวันเดียว พร้อมภาพหน้าจอ 2 ภาพ:

1. *"dark mode มันดูแปลกๆนะ ทำไมมันขาวๆแบบนั้น **มีจุดไหนในแอพเป็นบ้างก็ไม่รู้**"*
2. *"ทำไมช่องกรอกเวลาของ upcountry มันกว้างจนบังช่องให้ใส่สถานที่ไป **มีปัญหาตรงจุดอื่นอีกไหมไม่รู้**"*
3. *"ทั้งการใช้งานบนคอม และการใช้งานบนมือถือ ตรวจสอบให้แน่ชัดว่าหน้าตา interface ต่างๆ**ต้องไม่ล้นขอบ**
   และสามารถ**ปรับขนาดอัตโนมัติได้ตามขนาดที่ผู้ใช้งานใช้จริง** เพราะบางคนก็ปรับขนาด browser เล็ก บางคนก็ปรับใหญ่"*

คำว่า **"ก็ไม่รู้"** ที่ซ้ำสองครั้งคือหัวใจของงานนี้ สิ่งที่เขาขอไม่ใช่ "แก้สองจุดที่เห็น" แต่คือ
**"ไปหามาให้หมดว่ามีกี่จุด"** — เรื่องที่เขาเห็นเองคือตัวอย่าง ไม่ใช่ขอบเขต

สองจุดที่เขาเห็นถูกแก้ไปแล้วใน `4c3af05` และทั้งคู่มีต้นเหตุร่วมกันอย่างน่าสนใจ:

| จุด | ต้นเหตุ |
|---|---|
| ปุ่มขาวจ้าในโมดัลแก้ไขเวลา | สีถูกเขียนเป็น **inline style** บน element (`background:#f8fafc`) ซึ่งชนะ CSS ทุกกฎ ⇒ `[data-theme="dark"]` เอื้อมไม่ถึง |
| ช่องเวลา Upcountry บังช่องสถานที่ | ความกว้างถูกเขียนเป็น **inline style** บน `<input type="time">` ซึ่ง flatpickr ทิ้งไว้ข้างหลังตอนสร้าง element ใหม่บนมือถือ |

⇒ **ต้นเหตุเดียวกัน: การตั้งค่าหน้าตาด้วย inline style** ทำให้ CSS ที่เขียนไว้อย่างดี (ทั้งกฎโหมดมืด
และกฎ responsive) เอื้อมไปแก้ไม่ได้ · และโปรเจกต์นี้เคยบันทึกคลาสบั๊กนี้ไว้เองแล้วเมื่อ 2026-08-16
ในชื่อ **"#1e3a5f-class dark-mode bugs"** (`css/style.css:1705`) ⇒ เคยกวาดรอบหนึ่งแล้ว **แต่ยังเหลือ**

## เป้าหมาย

1. **รู้ให้ครบว่ามีกี่จุด** — รายการจุดที่พัง พร้อมหน้า/ธีม/ความกว้างที่ทำให้มันพัง วัดด้วยเครื่อง ไม่ใช่สายตา
2. **แก้จุดที่พัง** โดยย้ายค่าหน้าตาจาก inline style ไปเป็นกฎ CSS ที่ธีมและ breakpoint เอื้อมถึง
3. **มียามอัตโนมัติ** ที่ทำให้จุดเดิมพังซ้ำไม่ได้เงียบๆ — ไม่งั้นรอบหน้าเจ้าของต้องมาเป็นคนเจอเองอีก
   (นี่คือสิ่งที่รอบ 2026-08-16 ไม่ได้ทำ และเป็นเหตุผลที่ยังมีของเหลือมาถึงวันนี้)

## สิ่งที่ไม่ทำ (non-goals)

- **ไม่ออกแบบหน้าตาใหม่** ไม่เปลี่ยนสีแบรนด์ ไม่ย้ายตำแหน่งของอะไรที่ไม่ได้พัง — เจ้าของขอให้ของที่มี
  "ไม่พัง" ไม่ได้ขอของใหม่
- **ไม่แตะ layout ที่ผ่านเกณฑ์** แม้ผมจะคิดว่าสวยกว่าได้ · ความเห็นเรื่องความสวยไม่ใช่บั๊ก
- **ไม่ไล่แก้ inline style ทุกตัวในไฟล์** (`app.js` มี 578 บรรทัดที่มีสี inline) — แก้เฉพาะตัวที่
  **พิสูจน์ได้ว่าพังจริง** ในแกนใดแกนหนึ่ง การกวาดล้างทั้งหมดคือการเขียนแอปใหม่ ไม่ใช่สิ่งที่ถูกขอ

## สิ่งที่ถือว่าล้มเหลว (anti-goals)

- **รายงานว่า "กวาดครบแล้ว" ทั้งที่วัดไม่ครบ** — บทเรียนของโปรเจกต์นี้เองเมื่อ 2026-10-19:
  รายการ role ที่กวาดถูกหยิบจาก "บัญชีที่ล็อกอินได้" ไม่ใช่ "role ที่ระบบมีจริง" ทำให้ `marketing`
  หลุดไปเงียบๆ ⇒ **รายการหน้าที่จะกวาดต้องมาจาก index.html ไม่ใช่จากหน้าที่ผมนึกออก**
- **แก้แล้วทำของเดิมพัง** โดยเฉพาะบนเดสก์ท็อป ซึ่งเป็นเครื่องที่ฝ่ายบัญชีใช้ทำเงินเดือน
- **ไปแตะข้อมูลพนักงานจริง** ระหว่างการทดสอบ

## ข้อจำกัดที่ต้องเคารพ

- **ห้ามแก้ `Z:\Time_Attendance` ตรงๆ** ทำใน worktree เท่านั้น การขึ้นเว็บจริงต้องขออนุญาตเจ้าของทุกครั้ง
- **ห้ามเอาข้อมูลพนักงานจริงมาใช้ทดสอบ** และห้ามยิงเขียนใส่เซิร์ฟเวอร์จริง
- **ทุกข้อความที่ผู้ใช้เห็นต้องมีครบ 3 ภาษา** (TH/EN/JA) — ถ้าการแก้ทำให้เกิดข้อความใหม่
- **บัมพ์ cache-buster ทุกครั้งที่แตะไฟล์ frontend** (`?v=` ใน index.html + `APP_BUILD`)
- **`npm run check` ต้องจบที่ N/N เสมอ** และ `node --check attendance/js/app.js` หลังแตะ app.js ทุกครั้ง

## วิธีที่เสนอ

### 1. รันแอปในเครื่องด้วยข้อมูลปลอม (ไม่แตะของจริง)

`server.js:172` อ่านที่เก็บข้อมูลจาก environment variable:

```js
const DATA_DIR = process.env.DATA_DIR || path.join(__dirname, 'data');
```

⇒ ชี้ `DATA_DIR` ไปที่โฟลเดอร์ fixture ที่สร้างขึ้นเอง (พนักงานสมมติครบทั้ง 6 role, การลา, งวดเงินเดือน)
แล้วล็อกอินด้วยบัญชีสมมติ ⇒ เข้าถึงได้ทุกหน้าโดยไม่แตะ `users.json` จริงและไม่ยิงเว็บจริงเลยสักครั้ง

**ของที่ต้องสร้าง:** โฟลเดอร์ fixture + สคริปต์สร้างมันขึ้นใหม่ได้ (ไม่ commit ข้อมูลที่ดูเหมือนคนจริง)

### 2. รายการที่จะกวาด — มาจากไฟล์ ไม่ใช่จากความจำ

นับจาก `index.html` ของจริงแล้ว: **21 หน้า** (`id="page-*"`) และ **33 modal** (`class="modal-overlay"`)
รวม **54 จุด** · คูณด้วย 2 ธีม และความกว้างที่ทดสอบ ⇒ การกวาดต้องเป็นสคริปต์ ไม่ใช่การไล่คลิกมือ

### 3. เกณฑ์ว่า "อะไรเรียกว่าพัง" — ต้องวัดได้ด้วยเครื่อง

นี่คือส่วนที่ต้องตกลงกับเจ้าของก่อน เพราะถ้าไม่มีเกณฑ์ ผมจะไปไล่แก้ตามรสนิยมตัวเอง 93 จุด

| แกน | เกณฑ์ที่เสนอ | วัดยังไง |
|---|---|---|
| **โหมดมืด** | ข้อความกับพื้นหลังของมันมีอัตราส่วนความต่างต่ำกว่า **4.5:1** (มาตรฐาน WCAG AA สำหรับข้อความปกติ) | คำนวณจากสีที่เบราว์เซอร์ใช้จริง (`getComputedStyle`) ของทุก element ที่มีข้อความ |
| **โหมดมืด** | element ที่พื้นหลัง**สว่างกว่า**พื้นหลังของหน้า ทั้งที่อยู่ในโหมดมืด (= จุดขาวแบบที่เจ้าของเห็น) | เทียบความสว่างของพื้นหลัง element กับพื้นหลัง body |
| **ล้นขอบ** | ขอบขวา/ซ้ายของ element เลยขอบของกล่องที่ครอบมันอยู่ | `getBoundingClientRect()` เทียบกับพ่อ |
| **ล้นขอบ** | หน้ามีแถบเลื่อนแนวนอน | `documentElement.scrollWidth > innerWidth` |
| **ข้อความถูกตัด** | เนื้อในกว้าง/สูงกว่าช่องที่ใส่มัน | `scrollWidth > clientWidth` |
| **ปรับขนาดไม่ได้** | element มีความกว้างตายตัวที่กว้างกว่าจอ | ความกว้างที่คำนวณได้ เทียบกับ viewport |
| **ปุ่มเล็กเกินไปบนมือถือ** | ปุ่ม/ลิงก์สูงหรือกว้างต่ำกว่า **44px** | มีกฎนี้ใน `style.css` อยู่แล้ว (`.btn { min-height: 44px }` ในช่วงมือถือ) ⇒ ยามแค่บังคับให้เป็นจริง |

ความกว้างที่ทดสอบ (ตอบข้อ 5 ของเจ้าของเรื่องคนย่อ-ขยายหน้าต่าง): **320 · 375 · 414 · 600 · 768 · 1024 · 1280 · 1920**
— ไม่ใช่แค่ "มือถือกับคอม" เพราะจุดที่พังมักอยู่ตรงรอยต่อของ breakpoint ไม่ใช่ที่ขนาดมาตรฐาน

### 4. ลำดับการทำ

1. สร้าง fixture + รัน backend ในเครื่อง · พิสูจน์ว่าล็อกอินได้จริง
2. เขียนสคริปต์กวาด (Playwright) ที่เดินทุกหน้า × ทุกธีม × ทุกความกว้าง แล้วคายรายการจุดที่ตกเกณฑ์
3. **เอารายการให้เจ้าของดูก่อนแก้** — เพื่อให้เขาตัดสินว่าจุดไหนคือบั๊กจริง จุดไหนเขาตั้งใจให้เป็นแบบนั้น
   (บทเรียน 2026-10-17: เรื่องที่อยู่ GPS เป็นภาษาไทยเสมอ ดูเหมือนบั๊กแต่เป็นการตัดสินใจของเจ้าของ)
4. แก้ทีละกลุ่มตามต้นเหตุ ไม่ใช่ทีละ element · ทุกกลุ่มมียามของตัวเอง
5. รีวิวทั้ง branch ด้วยโมเดลที่แรงที่สุดก่อนเสนอขึ้นเว็บ

### 5. ยามที่จะเหลือไว้

สคริปต์กวาดในข้อ 2 **กลายเป็นยามถาวร** — เก็บไว้ใน `tests/` แล้วให้รันจุดที่เคยพังซ้ำทุกครั้งที่
`npm run check` ⇒ ของที่แก้แล้วพังซ้ำจะถูกจับได้เองโดยไม่ต้องรอเจ้าของมาเห็น

## สิ่งที่เหลือให้คนทำตัดสินเอง

- โครงสร้างของ fixture (ชื่อสมมติ จำนวนรายการ) ตราบใดที่ครอบทั้ง 6 role และไม่เหมือนคนจริง
- จะแก้ด้วย CSS class ใหม่ หรือใช้ CSS variable ที่มีอยู่ ตราบใดที่ผลลัพธ์ผ่านเกณฑ์ทั้งสองธีม
- ลำดับของกลุ่มที่แก้

## คำถามที่ต้องให้เจ้าของตอบก่อนเริ่ม

1. **เกณฑ์ความต่างของสี 4.5:1 ใช้ได้ไหม** หรืออยากให้เข้มกว่า/ผ่อนกว่านี้
   (ถ้าเข้มเกินไป ของที่ใช้งานได้ดีอยู่แล้วหลายจุดจะถูกนับว่าพัง)
2. **ต้องการดูรายการก่อนแก้ไหม** หรือให้แก้ไปเลยแล้วรายงานทีเดียวตอนจบ
3. ช่วงความกว้างที่ทดสอบครอบคลุมพอไหม — มีเครื่องรุ่นไหนในออฟฟิศที่ต้องเผื่อเป็นพิเศษหรือเปล่า
