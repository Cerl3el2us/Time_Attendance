## เป้าหมายที่เจ้าของตั้งไว้

เจ้าของพูดสองเรื่องในเซสชันวันที่ 2026-10-12

1. *"ทำไมเดี๋ยวนี้ถึงใช้เวลานานมากในการเริ่มงาน ติดขั้นตอนไหนยังไงบอกหน่อย"*
2. *"ทั้ง 2 เครื่องยังรู้ว่าทำงานถึงไหนแล้ว และ memory ทันกัน เพราะเมื่อก่อนเคยมีปัญหาอีกเครื่อง
   memory ไม่ทันกัน ทำให้เกิดการแก้งานซ้ำทั้งๆ ที่อีกเครื่องทำไปแล้ว และเวลาถามว่างานค้างอะไร
   อีกเครื่องไม่ค่อยรู้"*

พร้อมตัวอย่างที่ชี้ต้นเหตุได้ตรงที่สุด: *"เครื่องนี้เคยสั่งว่าหากรอบหน้าเปิดขึ้นมาให้เตือนเรื่อง
superadmin พอเข้างานไปเตือนอีกเครื่อง อีกเครื่องกลับไม่รู้ว่าคืออะไรให้ทำอะไร"*

เคสนั้นไม่ใช่ "memory ไม่ทัน" — **โน้ตเดินทางไปถึงจริง แต่เนื้อหาไม่ได้เดินทางไปด้วย**
ประโยค "รอบหน้าเตือนเรื่อง superadmin" อ่านรู้เรื่องเฉพาะกับเครื่องที่เพิ่งคุยกันมา
นี่คือความผิดพลาดรูปแบบเดียวกับกฎของ `MEMORY.md` ที่ว่าสารบัญห้ามอ้างสถานะ: **ตัวชี้ที่ไม่มีของจริงอยู่ข้างใน**

## ขอบเขต — 9 ข้อ เรียงตามลำดับที่จะลงมือ

### 1. หั่น `STATUS.md`

`STATUS.md` เหลือสามหัวข้อ: `## ส่งต่อรอบหน้า` · `## เปิดอยู่` · `## ปิดแล้ว (สารบัญ)`
โดยสารบัญเก็บ **1 บรรทัดต่อข้อ** (วันที่ + ชื่อเรื่อง + ลิงก์ไปหัวข้อในไฟล์รายละเอียด)
รายละเอียดทั้ง 406 บรรทัดย้ายไป `docs/STATUS_CLOSED.md` โดย**ไม่แก้เนื้อหา**

**ทำไมไม่ตัดทิ้งเลย:** หน้าที่ของหัวข้อ "ปิดไปแล้ว — อย่าเสนอซ้ำ" คือกันการเสนองานที่ทำเสร็จแล้ว
ซึ่งเคยพังจริง (เจ้าของเคยต้องสั่งแก้งานที่เสร็จไปตั้งแต่กรกฎาคม) สารบัญ 1 บรรทัดทำหน้าที่นี้ได้ครบ

**เกณฑ์รับ:** `STATUS.md` ≤ 150 บรรทัด และ ≤ 20 KB · ทุกข้อในสารบัญมีหัวข้อปลายทางอยู่จริงใน
`docs/STATUS_CLOSED.md` · **ทุกข้อใน `## เปิดอยู่` ถูกเติมบรรทัด `· ตรวจ: <check-id>` ตอนหั่นไฟล์นี้**
(รูปแบบตามข้อ 7) ไม่ใช่ค่อยไปเติมทีหลัง

### 5. เร่งการเทียบไฟล์ใน `sync_memory.ps1`

`Test-SameContent` เปลี่ยนเป็น

1. **ขนาดต่างกัน ⇒ ต่างกันแน่** ไม่ต้อง hash
2. **ขนาดเท่าและเวลาเท่า (เทียบ `LastWriteTimeUtc.Ticks` เต็มความละเอียด) ⇒ ถือว่าเหมือน** ข้ามไป
3. **ขนาดเท่าแต่เวลาต่าง ⇒ hash เพื่อตัดสิน** (นี่คือเคสที่ hash ยังจำเป็น)

**ข้อแลกเปลี่ยนที่ต้องพูดตรงๆ:** ข้อ 2 พลาดได้ในกรณีเดียว — ไฟล์ถูกแก้แล้วได้ขนาดเท่าเดิม
*และ* มี timestamp ตรงกันถึงระดับ tick ซึ่งเกิดได้จาก `Copy-Item` ที่รักษา mtime ต้นทาง
(= เนื้อหาเหมือนกันอยู่แล้ว) การเทียบที่ระดับ tick ไม่ใช่วินาที ทำให้โอกาสพลาดจากการแก้มือหายไป
แต่ไม่เป็นศูนย์ ⇒ **ยอมรับความเสี่ยงนี้** เพราะ `.sync_backup\` และ git บน NAS ยังเป็นตาข่ายรอง

**ห้ามเสียของเดิม:** `-ge` (ไม่ใช่ `-gt`) · `-ErrorAction Stop` ทุกจุด · สำรองก่อนทับขา pull ·
ข้ามไฟล์ที่ปลายทางย้ายเข้า `archive\` แล้ว · **คำเตือนต้องพิมพ์ก่อนบรรทัดสรุป** และบรรทัดสุดท้าย
ต้องสรุปครบในตัวเอง (`session_start.ps1` หยิบบรรทัดสุดท้ายที่ไม่ว่างไปใส่ hook)

**เกณฑ์รับ:** เวลาเปิด session บน LAN จาก ~4.2 วิ เหลือ **≤ 1 วิ** เมื่อไม่มีไฟล์เปลี่ยน

### 6. push memory อัตโนมัติ

เจ้าของเคยสั่ง 2026-10-05 ว่า *"ไม่จำเป็นต้อง push memory ทุกครั้งที่ทำเสร็จ อยากให้ push
เวลาสั่งจบงาน"* หลังเคยมีเซสชันที่ push 5 ครั้งในนั่งเดียว

**เจ้าของแก้เหตุผลเองเมื่อ 2026-10-12:** *"ไม่ได้รำคาญ สามารถมีข้อความได้ แค่ตอนแรกรู้สึกว่า
มันกินเวลานานมาก ถ้าต้องทำทุกครั้ง"*

⇒ **ข้อจำกัดจริงคือเวลา ไม่ใช่ข้อความ** · เอกสารและ memory เดิมที่บันทึกว่าเหตุผลคือ
"เสียงรบกวน" เป็นการตีความของ Claude เอง ไม่ใช่คำของเจ้าของ (แก้ใน
`feedback_attendance_memory_sync.md` แล้ววันเดียวกัน)

สิ่งที่สเปกนี้ต้องรับประกันจึงเป็น **งบเวลา** ไม่ใช่ความเงียบ

| สถานการณ์ | งบเวลาที่ยอมรับ | วัดได้จริง |
|---|---|---|
| เทิร์นที่ memory ไม่เปลี่ยน (ส่วนใหญ่) | ≤ 0.1 วิ | 0.042 วิ (อ่าน C: เท่านั้น) |
| เทิร์นที่ memory เปลี่ยน | ≤ 1 วิ | ~0.4 วิ หลังทำข้อ 5 |

**เรื่องข้อความ:** ไม่ต้องเงียบก็ได้ แต่ `Stop`/`SessionEnd` ไม่มีช่องทางที่เชื่อถือได้ในการ
พิมพ์ให้เจ้าของเห็นในแชต ⇒ ที่ทำได้จริงคือ **จดลง `Z:\claude_memory\sync.log` แล้วให้
`npm run backlog` อ่านมาแสดง** และ **Claude พูดเองหนึ่งบรรทัดในเทิร์นที่มันเขียน memory**
ว่าเขียนอะไรไว้ (hook จะ push ให้หลังเทิร์นจบ) ⇒ เจ้าของได้ข้อความตรงจังหวะที่มีความหมาย
ไม่ใช่ข้อความซ้ำๆ ที่ไม่มีข้อมูลใหม่

| hook | ทำอะไร | ต้นทุน |
|---|---|---|
| `Stop` (ยิงทุกครั้งที่ผมตอบจบ) | อ่านขนาด+เวลาของ memory **บน C: เท่านั้น** เทียบกับหมุด `C:\Users\<user>\.claude\projects\Z--\.sync_marker` · ไม่มีอะไรใหม่ ⇒ ออกทันที **ไม่แตะ NAS** | 0.042 วิ |
| `Stop` เมื่อมีไฟล์ใหม่กว่าหมุด | `sync_memory.ps1 push -ProjectDir "Z:\"` แล้วอัปเดตหมุด · ผลลง `Z:\claude_memory\sync.log` | ~0.4 วิ |
| `SessionEnd` (`clear`/`resume`/`logout`/`prompt_input_exit`/`other`) | ทำอย่างเดียวกันอีกชั้น เผื่อเทิร์นสุดท้ายแก้ memory แล้วปิดเลย · ตั้ง `timeout` เอง เพราะงบเริ่มต้นของ `SessionEnd` คือ 1.5 วิ (ขยายได้ถึง 60) | ~0.4 วิ |

**ทำไมต้องมีทั้งสองตัว:** `SessionEnd` ยิงเฉพาะเมื่อ session จบจริง ถ้าปล่อยแท็บค้างข้ามวันหรือ
ปิดแอปกระทันหัน มันไม่ยิง · `Stop` ยิงแน่นอนแต่ถี่ ⇒ ใช้ `Stop` เป็นตัวหลักโดยทำให้มันเกือบฟรี
และ `SessionEnd` เป็นตัวปิดท้าย

**ข้อบังคับ:** ทั้งสองต้องไม่พิมพ์อะไรเข้า context ของ Claude (เหตุผลทางเทคนิค ไม่ใช่เพื่อปิดบัง

4. พิมพ์ผลเป็น **ตาราง `ขนาด | งาน`** ตามคำสั่งเจ้าของใน `feedback_pending_task_format.md`
5. ปิดท้ายด้วยบล็อก **สุขภาพการ sync** (ข้อ 8)

`.claude/commands/backlog.md` เป็นตัวบาง: สั่งรัน `npm run backlog` แล้ว **ห้ามสรุปงานค้าง
ก่อนเห็นผลลัพธ์จริง** (ตามสเปก 4.6 เดิมที่กำหนดว่าห้ามตอบก่อนไล่ตรวจพร้อมหลักฐานครบทุกข้อ)

**ต้องตัด `node_modules` ทุกการค้นในสคริปต์** — เป็นตัวที่ทำให้คำสั่งค้นตายไป 120 วิในเซสชันนี้

**งบเวลาของสคริปต์: ≤ 5 วินาที** · ชิ้นส่วนที่วัดไว้แล้ว 2026-10-12: `node` เริ่มทำงาน 0.1 วิ ·
อ่าน `STATUS.md` ที่หั่นแล้ว ~0.15 วิ · `git status` + นับ commit ที่ยังไม่ push บน worktree
ในเครื่อง **1.94 วิ** · เทียบรายชื่อ+ขนาด memory สองฝั่ง 0.22 วิ · อ่านบรรทัดท้าย `sync.log` 0.02 วิ
⇒ เหลืองบให้การตรวจรายข้อประมาณ 2.5 วิ

**ข้อที่ต้องพูดตรงๆ ในสเปก:** `/backlog` **เพิ่ม** เวลาเครื่องประมาณ 3 วิ ⇒ เวลาเครื่องรวม
ลดจาก ~4.8 วิ เหลือ ~3.5 วิ เท่านั้น **กำไรจริงไม่ได้อยู่ที่วินาทีของดิสก์** แต่อยู่ที่จำนวนรอบ
ที่ Claude ต้องคุยกับโมเดลก่อนตอบคำถามแรกได้ (วัดจากเซสชัน 2026-10-12: **7–8 รอบ + timeout
120 วิ** ⇒ เป้า **2 รอบ**) และปริมาณข้อความที่ต้องขนในรอบเหล่านั้น (~100 KB ⇒ ~14 KB)
· ถ้าใครมาวัดผลงานนี้ด้วย "เวลาเครื่องลดลงกี่วิ" จะสรุปผิดว่าแทบไม่ได้อะไร

**ถ้า `git` กินงบเกิน:** ตัดเหลือ `git status --porcelain -- STATUS.md` อย่างเดียว
และนับ commit ที่ยังไม่ push แบบ `git rev-list --count @{u}..HEAD` ครั้งเดียว ห้ามเรียก git ซ้ำ
หลายรอบ เพราะค่าเริ่มโปรเซสบน Windows ประมาณ 0.3 วิต่อครั้ง

### 8. บล็อกสุขภาพการ sync — ทำให้ "ไม่ตรงกัน" ดังขึ้นมาเอง

ส่วนท้ายของ `npm run backlog` รายงาน

- **memory:** ไฟล์ที่เนื้อหาต่างกับ NAS · ไฟล์ที่มีแต่ในเครื่อง (= งานที่ยังไม่ขึ้น NAS)
- **ไฟล์ที่ถูกลบฝั่งเดียว:** NAS มีแต่เครื่องนี้ไม่มี และกลับกัน — **รายงานเท่านั้น ไม่ลบอัตโนมัติ**
  เพราะ `sync_memory.ps1` ไม่มี logic ลบทั้งสองทิศทางโดยเจตนา และการให้สคริปต์ลบเองคือทางที่
  ข้อมูลหายถาวร (เคยเกือบพัง `archive\` ด้วยเหตุนี้) ⇒ ให้เจ้าของตัดสิน
- **ไฟล์ memory ที่ไม่เข้า `$Patterns`** ⇒ ฟ้องว่า "ไฟล์นี้จะไม่ถูก sync" **กันรูปแบบของบั๊ก
  ไม่ใช่กันเคสเดียว** (ยกเว้นไฟล์ที่ขึ้นต้นด้วยจุด เช่น `.sync_backup`)
- **git:** commit ที่ยังไม่ push · `STATUS.md` ที่แก้แล้วแต่ยังไม่ commit
- **บรรทัดสุดท้ายของ `sync.log`** + เตือนถ้ารอบล่าสุดมีไฟล์ชนกัน

**ข้อจำกัดที่ต้องเขียนไว้ในผลลัพธ์เอง:** ถ้าอีกเครื่องยังไม่ push เครื่องนี้ไม่มีทางรู้ว่ามีอะไร
ค้างอยู่ที่นั่น — เป็นข้อจำกัดเชิงกลไก ข้อ 6 คือสิ่งที่ทำให้โอกาสนั้นเล็กลง ไม่ใช่หายไป

เจ้าของอนุมัติแยกเมื่อ 2026-10-12 · เป็น memory ของโปรเจกต์อื่นตามกฎ "ห้ามแตะ" จึงต้องขออนุมัติก่อน
· ลบผ่าน git ของ `Z:\claude_memory` เพื่อให้ยังย้อนดูได้

**ตรวจแล้ว 2026-10-12: ไฟล์นี้ไม่มีสำเนาในเครื่องนี้** (เป็น 1 ใน 9 ไฟล์ที่มีแต่บน NAS เพราะไม่เข้า
`$Patterns`) ⇒ ไม่มีอะไรต้องลบฝั่งเครื่อง และไม่มีความเสี่ยงว่าจะถูก push กลับขึ้นไป
**แต่เครื่องบ้านต้องตรวจเองซ้ำ** เพราะเครื่องนี้มองสำเนาของเครื่องนั้นไม่เห็น
