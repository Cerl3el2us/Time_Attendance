# แก้เวลาเข้างานโดย accounting/md — สเปกการออกแบบ

วันที่ 2026-10-14 · เจ้าของสั่ง และตอบคำถามออกแบบแล้วก่อนออกจากงาน

## คำตอบของเจ้าของ (คำต่อคำ)

> จะกดแก้ได้กับ case ที่มีการผ่านประตูตั้งแต่ 05.30-07.30 และจะแก้เป็นเวลาอะไรก็ได้
> แต่ต้องมีเหตุผลและประวัติการแก้ ซึ่งโดยส่วนใหญ่ ถ้าแก้ จะแก้เป็นหลังจากเวลาที่ผ่าน
> เช่นมาผ่านตอน 07.00 แต่อาจจะแก้ให้เป็น 08.30 แทน

บวกกับข้อเดิมใน `STATUS.md`: ของ accounting เอง **มีแต่ MD ที่แก้ได้**

## สิ่งที่ตรวจพบในโค้ดจริงก่อนออกแบบ

| เรื่อง | ความจริง |
|---|---|
| มีกลไกแก้เวลาอยู่แล้วไหม | **มี แต่คนละอย่าง** — `time-correction` เป็น**คำขอที่ต้องให้ MD อนุมัติ** (`APPROVAL_ROUTING['time-correction'] = ['md']`) ที่เจ้าของสั่งคือแอดมินกดแก้เองทันที ไม่ต้องรออนุมัติ |
| ฟีเจอร์ที่ใกล้เคียงที่สุด | `checkout-reviews` — ไฟล์แยก คีย์ `${userId}_${date}` + handler lock + GET ที่ scope ตาม role |
| จุดคอขวดของข้อมูลวันทำงาน | `buildAttendanceLogForUser()` ฝั่ง server · `loadAttendanceFromBackend()` ฝั่งเว็บ |

## การตัดสินใจ และเหตุผล

### 1. เป็น "ชั้นทับ" ไม่ใช่การแก้ข้อมูลสแกน

ไม่เขียนทับ event จากเครื่องสแกน ⇒ เวลาผ่านประตูจริงยังอยู่ครบ และวันที่แก้ไปแล้วยังแก้ซ้ำได้
เพราะเงื่อนไข 05:30–07:30 ตรวจจาก **เวลาเดิม** ไม่ใช่เวลาที่แก้แล้ว

### 2. ใส่ที่จุดคอขวดจุดเดียวของแต่ละฝั่ง

payroll / ประตูตอกบัตร / ตาราง / สลิป เห็นเวลาที่แก้แล้วเองทั้งหมด โดยไม่มีจุดไหนต้องรู้ว่าฟีเจอร์นี้มีอยู่
และไม่มีจุดเรียกไหนถูกลืมได้ · `applyCheckinEdits()` **dual-sync** เพราะมันตัดสินเงิน

### 3. "ห้ามแก้ของตัวเอง" คือกลไกที่ส่งมอบกฎของเจ้าของ

accounting แก้ของคนอื่นได้แต่ของตัวเองไม่ได้ ⇒ **เหลือแต่ MD ที่แก้ของ accounting ได้** ตรงตามที่สั่ง
โดยไม่ต้องเขียนกฎเฉพาะกิจของ role ไหนเป็นพิเศษ

### 4. ข้อที่ผมตัดสินเองเพราะเจ้าของไม่อยู่ — ต้องรีวิว

| ตัดสินว่า | เหตุผล | ถ้าผิดจะเสียอะไร |
|---|---|---|
| **งวดที่ล็อก / accounting ยืนยันภาษีแล้ว / MD อนุมัติแล้ว → ปฏิเสธ** | ตามแบบแผนเดียวกับ `checkout-reviews` และกันการแก้ย้อนหลังงวดที่จ่ายไปแล้ว | ถ้าเจ้าของอยากให้แก้ได้ ต้องเปิดช่องเพิ่ม |
| **แก้ได้เฉพาะเวลาเข้า ไม่รวมเวลาออก** | ขอบเขตที่เจ้าของเขียนคือ "เวลาเข้างาน" | ถ้าอยากได้เวลาออกด้วย ต้องทำเพิ่ม |
| **เหตุผลยาวได้ไม่เกิน 500 ตัวอักษร** | ตัวเลขทั่วไป ป้องกันไฟล์บวม | ปรับได้ง่าย |
| **พนักงานเห็นรายการแก้ของวันตัวเองได้** | เวลาที่แก้คือเวลาเข้างานของเขา ถ้าซ่อนไว้ หน้าจอจะโชว์ตัวเลขที่เขาอธิบายไม่ได้ | ถ้าอยากให้เห็นเฉพาะแอดมิน ต้องแก้ scope ของ GET |
| **คำขอ `time-correction` ที่อนุมัติแล้ว ทับการแก้ตรงนี้** | เป็นเส้นทางเดิมที่ผ่านการอนุมัติ ไม่เปลี่ยนลำดับของฟีเจอร์ที่มีอยู่โดยไม่ได้สั่ง | หน้าจอจึง **เตือน** เมื่อวันนั้นมีคำขอที่อนุมัติแล้ว ไม่งั้นแก้แล้วไม่มีผลโดยไม่รู้ตัว |

### 5. ประวัติอยู่กับตัวระเบียน ไม่ใช่ log แยก

ทุกครั้งที่แก้จะ append `{from, to, reason, by, byId, at}` ⇒ ประวัติไม่มีทางหลุดจากค่าที่มันอธิบาย

## เทสต์ที่ต้องมี

1. หน้าต่าง 05:30–07:30 ตรงกันทั้งสองฝั่งถึงระดับนาที
2. role ที่ไม่ใช่ md/accounting ถูกปฏิเสธ · ห้ามแก้ของตัวเอง · MD แก้ของ accounting ได้
3. งวดที่ล็อกถูกปฏิเสธ
4. เหตุผลบังคับ และยาวเกินถูกปฏิเสธ (ไม่ตัดเงียบ)
5. เวลาใหม่ต้องเป็นเวลาจริง แต่เป็นเวลาใดก็ได้ตามที่เจ้าของสั่ง
6. ชั้นทับเปลี่ยนเวลาเข้า เก็บเวลาเดิมไว้ ไม่แตะอย่างอื่น และ **สองเครื่องให้ผลเหมือนกัน**
7. ชั้นทับถูกเรียกจริงในตัวประกอบข้อมูลของทั้งสองฝั่ง ไม่ใช่แค่ในเทสต์
8. ประวัติถูก append เท่านั้น

## สิ่งที่จงใจไม่ทำ

- ไม่แตะกลไกคำขอ `time-correction` เดิม
- ไม่เขียนทับ event ของเครื่องสแกน
- ไม่ทำให้การแก้ย้อนกลับไปแก้งวดที่ปิดไปแล้ว
