# แบบ: บังคับลาเป็นชั่วโมงเต็ม (ยกเลิกการลารายนาที)

**วันที่:** 2026-11-03 · **ผู้ตัดสิน:** เจ้าของ (ทุกข้อใน "กฎที่เจ้าของตัดสิน" ด้านล่าง)
**เริ่มใช้จริง:** รอบมกราคม 2027 (ตั้งค่าได้ ไม่ฝังในโค้ด)

## โจทย์

เจ้าของได้รับคำสั่งให้ปรับการยื่นวันลา ให้ลาได้เป็น **ชั่วโมงเต็ม** เท่านั้น (1 ชม. / 2 ชม. / 3 ชม. …)
ยกเลิกการลารายนาที

## สภาพเดิม (ตรวจกับโค้ดจริง 2026-11-03 ไม่ใช่จากเอกสาร)

| เรื่อง | ค่าที่ใช้จริง | ที่มา |
|---|---|---|
| เวลางาน | 08:30–17:30 | `appSettings.workSchedule.standardStartHour/Minute` = 8/30 · เวลาเลิก 17:30 **ฝังในโค้ด** |
| พักเที่ยง | 12:00–13:00 **ไม่คิดเป็นเวลาลา** | `hourlyLeaveChargedMinutes()` ทั้งสองฝั่ง (เจ้าของตัดสิน 2026-09-24) |
| 1 วันลา | 8 ชั่วโมง = 480 นาที | `leaveRecordMinutes()` / `leaveMinutesOf()` |
| ช่องกรอก | `<input type="time">` เลือกได้ทุกนาที | `index.html` `#leave-form-start` / `#leave-form-end` |
| ปุ่มลัด | ครึ่งวันเช้า `08:30–12:00` (3.5 ชม.) · ครึ่งวันบ่าย `13:00–17:30` (4.5 ชม.) | `setHalfDayLeave()` |
| ด่านตรวจที่มี | สิ้นสุด > เริ่ม · วันเดียว · ไม่อยู่ในพักเที่ยงทั้งช่วง | `submitLeave()` + `hourlyLeaveShapeError()` |
| ด่านเรื่องความลงตัวของชั่วโมง | **ไม่มีเลย** | — |
| เพดานชั่วโมงต่อใบ | **ไม่มีเลย** | — |

**ข้อมูลจริงในระบบ** ใบลารายชั่วโมงมีทั้งหมด 4 ใบ: `08:30–12:00` (3.5 ชม.) สามใบ และ `08:30–09:08`
(38 นาที) หนึ่งใบที่ยัง `pending-md` ⇒ ของที่คนใช้จริงคือปุ่มครึ่งวันเช้า

## ปัญหาที่ทำให้ "ชั่วโมงเต็ม" ไม่ใช่เรื่องเพิ่มด่านเฉยๆ

เช้าทำงาน 08:30–12:00 = **3.5 ชม.** · บ่ายทำงาน 13:00–17:30 = **4.5 ชม.**
⇒ ครึ่งวันทั้งสองฝั่งไม่ใช่จำนวนชั่วโมงเต็ม ถ้าบังคับชั่วโมงเต็มตรงๆ **ปุ่มที่คนใช้มากที่สุดจะใช้ไม่ได้**

## กฎที่เจ้าของตัดสิน (2026-11-03)

1. **วันเริ่มบังคับตั้งค่าได้** และด่านตัดสินจาก **วันที่ลา** (`dateFrom`) ไม่ใช่วันที่กดยื่น
   เหตุผลที่เจ้าของให้: *"ลาพักร้อนที่เหลือในปีนี้ ยังอนุญาตให้ลาเป็นนาทีได้อยู่"* ⇒ คนที่ยื่นใบลา
   ของเดือนธันวาคมในเดือนมกราคม ต้องยังยื่นแบบเดิมได้
2. **จุดแบ่งครึ่งวันย้ายมาที่ 13:30** — ลาครึ่งวันเช้า = `08:30–13:30` (คิด 4 ชม. เพราะหักพักเที่ยง) ⇒
   กลับมาทำงาน 13:30 · ลาครึ่งวันบ่าย = `13:30–17:30` (4 ชม.)
   ⇒ ครึ่งวันกลายเป็น 4+4 = 8 ชม. **เป็นชั่วโมงเต็มทั้งคู่ ไม่ต้องมีข้อยกเว้นใดๆ**
3. **ฟอร์มเปลี่ยนเป็น "เวลาเริ่ม + จำนวนชั่วโมง"** ระบบคำนวณเวลาสิ้นสุดให้ ⇒ กรอกผิดไม่ได้
4. **เวลาเริ่มเลือกได้ทุกครึ่งชั่วโมง** (08:30, 09:00, 09:30 …) เข้ากันกับเวลาเริ่มงาน 08:30
   และจุดแบ่งครึ่งวัน 13:30 พอดี
5. **เพดาน 7 ชม./ใบ** — ถ้าจะลา 8 ชม. คือลาเต็มวัน ต้องใช้โหมด "ลาเป็นวัน" ซึ่งนับวันหยุด/
   วันหยุดนักขัตฤกษ์ให้ถูกต้อง (โหมดชั่วโมงบันทึก `days=0` และทำให้รายงานนับวันลาเพี้ยน)
6. **ปุ่มครึ่งวันของวันลาก่อนวันบังคับ คงเวลาเดิม** `08:30–12:00` / `13:00–17:30` — วันลาก่อนวันเริ่ม
   บังคับคือกฎเก่าทั้งหมด ไม่มีอะไรเปลี่ยนกลางรอบเงินเดือน

## แบบ

### 1. ค่าตั้งใหม่ค่าเดียว

`appSettings.leave.wholeHourLeaveFrom` : สตริง `"YYYY-MM-DD"` · ค่าเริ่มต้น `""` = **ปิดสนิท**
(ของเดิมทำงานเหมือนเดิมทุกอย่าง) · ตั้งเป็น `"2027-01-01"` เมื่อถึงเวลาใช้

ต้องลงทะเบียน 3 ที่:
- `DEFAULT_APP_SETTINGS.leave` ใน `server.js` (~บรรทัด 27)
- ด่านตรวจค่าตั้งตอน `PUT` ใน `server.js` (~บรรทัด 5105) — รับเฉพาะ `""` หรือ `YYYY-MM-DD` ที่เป็นวันจริง
- ช่องตั้งค่าในหน้าตั้งค่าฝั่งหน้าเว็บ

### 2. ฟังก์ชันร่วม (DUAL-SYNC app.js ↔ server.js)

```
wholeHourLeaveRequired(dateStr)    -> bool    // dateStr >= wholeHourLeaveFrom (และค่าตั้งไม่ว่าง)
hourlyLeaveEndFromHours(start, h)  -> 'HH:MM' // คำนวณเวลาสิ้นสุด ข้ามพักเที่ยงให้เอง
wholeHourLeaveError(start, end)    -> msg|null // ด่านตรวจ
```

**สูตรคำนวณเวลาสิ้นสุด** (ให้ผลตรงกับ `hourlyLeaveChargedMinutes()` ที่มีอยู่ ไม่แก้สูตรเดิม):

```
need = h * 60
ถ้า start >= 13:00            -> end = start + need
ถ้า start + need <= 12:00     -> end = start + need
นอกนั้น (คร่อมพักเที่ยง)       -> end = start + need + 60
```

ตรวจแล้วว่าให้ผลถูกทุกกรณีที่ต้องใช้:

| เริ่ม | ชั่วโมง | สิ้นสุด | คิดเป็น |
|---|---|---|---|
| 08:30 | 3 | 11:30 | 3 ชม. |
| 08:30 | 4 | **13:30** | 4 ชม. (= ครึ่งวันเช้า) |
| 13:30 | 4 | **17:30** | 4 ชม. (= ครึ่งวันบ่าย) |
| 10:00 | 3 | 14:00 | 3 ชม. (ไม่ใช่ 13:00) |
| 11:30 | 1 | 13:30 | 1 ชม. |

### 3. ด่านตรวจ (เฉพาะเมื่อ `wholeHourLeaveRequired(dateFrom)` เป็นจริง)

| เงื่อนไข | ที่มา |
|---|---|
| เวลาที่คิดได้ ต้องหาร 60 ลงตัว | กฎหลักที่เจ้าของสั่ง |
| ไม่เกิน 7 ชม. | ข้อ 5 |
| เวลาเริ่มอยู่บนกริดครึ่งชั่วโมง | ข้อ 4 |
| เวลาเริ่มไม่อยู่ในพักเที่ยง 12:00–12:59 | พักอยู่แล้ว ไม่ต้องลา |
| ทั้งช่วงอยู่ในเวลางาน (เริ่ม ≥ 08:30, สิ้นสุด ≤ 17:30) | ผลพลอยได้ของข้อ 3-4 — เดิมไม่มีด่านนี้ |

วางไว้ทั้งสองฝั่ง: `submitLeave()` (app.js) และ `hourlyLeaveShapeError()` (server.js)
ฝั่ง server ครอบทั้ง `POST /api/leaves` (บรรทัด 6882) และ `PUT` ตอนแก้ใบ (บรรทัด 7852) อยู่แล้ว
เพราะทั้งคู่เรียกฟังก์ชันเดียวกัน — **ตรวจแล้ว ไม่ได้เดา**

### 4. ฟอร์ม — ทำแบบไม่แตะโครงเดิม

`#leave-form-start` / `#leave-form-end` ยังเป็นแหล่งข้อมูลจริงเหมือนเดิม **ไม่เปลี่ยนชื่อ ไม่ย้าย**
เพิ่ม `<select>` สองตัวที่ *เขียนค่าลงช่องเดิม* แล้วเรียก `calcLeaveHours()` ต่อ:

- `#leave-form-start-slot` — ตัวเลือกทุกครึ่งชั่วโมง 08:30 … 16:30 (ข้าม 12:00 / 12:30)
- `#leave-form-hours` — 1–7 ตัดตัวเลือกที่ทำให้เลยเวลาเลิกงานออก
- ข้อความ `#leave-form-end-computed` บอกผล *"สิ้นสุด 14:00"*

เมื่อบังคับ: ซ่อนสองช่องเวลาเดิม แสดงคู่ `<select>` · เมื่อไม่บังคับ: กลับเป็นของเดิมเป๊ะ
⇒ `submitLeave()`, `calcLeaveHours()`, `setHalfDayLeave()`, `editLeaveRequest()` **ทำงานกับช่องเดิม
ต่อไปได้โดยไม่ต้องแก้ตรรกะ** ซึ่งเป็นเหตุผลที่เลือกวิธีนี้แทนการเปลี่ยน `<input>` เป็น `<select>`

### 5. ใบเก่าและการแก้ใบ

- **ไม่ตรวจย้อนใบเก่า** ใบที่ยื่นไปแล้วเป็นรายนาที อยู่เฉยๆ ไม่ถูกแตะ ไม่ถูกปฏิเสธย้อนหลัง
- ตอนกดแก้ใบ `editLeaveRequest()` แปลง `hourlyStart`/`hourlyEnd` กลับเป็น "เริ่ม + จำนวนชั่วโมง"
- ถ้าแปลงไม่ลงตัว (เช่นใบ 38 นาทีที่ยังค้าง) และวันลายังอยู่ก่อนวันบังคับ → ใช้ฟอร์มเดิม
- ถ้าวันลาเลยวันบังคับแต่ค่าไม่ลงตัว → แสดงฟอร์มใหม่และให้เลือกใหม่ (ด่านจะปฏิเสธถ้าไม่แก้)

### 6. สิ่งที่จะ **ไม่** แตะ

- **สูตรเงินและการนับสิทธิ์** (`leaveRecordMinutes`, `leaveMinutesOf`, `hourlyLeaveChargedMinutes`)
  กฎใหม่ทำให้เวลาที่คิดได้เป็นชั่วโมงเต็มอยู่แล้ว สูตรเดิมรับได้ ⇒ ความเสี่ยงต่อเงินเดือน = 0
- **การนับสิทธิ์ข้ามปี** `docs/design-history/LEAVE_SUBMISSION_REVIEW_FOR_SONNET.md:124` เตือนว่า
  การนับสิทธิ์ไม่กรองปีและ *"จะระเบิดต้นปี 2027"* ซึ่งเป็นรอบเดียวกับที่กฎนี้เริ่มใช้ —
  **เป็นงานแยก ต้องตรวจกับโค้ดจริงว่ายังจริงไหม ก่อนจะสรุปอะไร**
