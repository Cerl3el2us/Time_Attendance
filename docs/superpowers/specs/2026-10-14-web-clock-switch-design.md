# ปิด/เปิด การตอกบัตรผ่านเว็บ — สเปกการออกแบบ

วันที่ 2026-10-14 · เจ้าของสั่ง · เจ้าของตอบคำถามออกแบบครบแล้วก่อนออกจากงาน

## สิ่งที่ต้องได้

สวิตช์ปิดการเช็กอิน-เช็กเอาต์ผ่านเว็บ · ปิดแล้วส่วนตอกบัตรบนมือถือต้องหายไป และทุกคนสแกนหน้าที่
เครื่องในออฟฟิศ · **ซ่อนปุ่มอย่างเดียวไม่พอ server ต้องปฏิเสธด้วย** ไม่งั้นเป็นภาพลวงตา

## คำตอบของเจ้าของ (2026-10-14)

| คำถาม | คำตอบ |
|---|---|
| ขอบเขตสวิตช์ | ปิดทั้งบริษัทได้ แต่ถามกลับว่ายกเว้นรายตำแหน่งยากไหม |
| คนที่เช็กอินเว็บไปแล้ว | **คงไว้ทั้งหมด ใช้ได้ตามปกติ** |
| geofence | **เก็บไว้เหมือนเดิม ไม่แตะ** |

## สิ่งที่ตรวจพบในโค้ดจริง (ไม่ใช่การเดา)

| เรื่อง | ความจริง |
|---|---|
| ใครตัดสินการตอกบัตรผ่านเว็บฝั่ง server | `webScanGateReason(hikUser, eventTimeIso, gps, gpsAgeSecRaw)` — เป็นเจ้าของการตัดสินทั้งหมด คืน reason แล้วตัวเรียกแปลงเป็น 403 |
| ฝั่งเว็บ | `geofenceUiState()` เป็นคู่แฝดของมัน และ `geofenceMessage(reason)` แปลข้อความตาม reason อยู่แล้ว |
| แบบแผนยกเว้นรายตำแหน่ง | **มีอยู่แล้ว** — `geofence.exemptRoles: ['driver']` |
| ทำไม driver ถูกยกเว้น geofence | เพราะไม่ได้อยู่ออฟฟิศ ⇒ **ปิดทั้งบริษัทจะทำให้ driver เช็กอินไม่ได้เลย** |

## การตัดสินใจ และเหตุผล

### 1. ยกเว้นรายตำแหน่งได้ และตั้งต้นยกเว้น `driver`

**ตอบคำถามที่เจ้าของถามกลับ: ยกเว้นรายตำแหน่งแทบไม่ยากกว่าเลย** เพราะ `geofence.exemptRoles`
ใช้แบบแผนนี้อยู่แล้วในไฟล์เดียวกัน · และ **จำเป็นด้วย** ไม่ใช่แค่ทางเลือก เพราะ driver ถูกยกเว้น
geofence ไว้อยู่แล้วด้วยเหตุผลว่าไม่ได้อยู่ออฟฟิศ ⇒ ปิดทั้งบริษัทคือการตัดช่องตอกบัตรของ driver ทิ้ง

```
webClock: { enabled: true, exemptRoles: ['driver'] }
```

ส่งมอบ `enabled: true` ⇒ **deploy แล้วไม่มีอะไรเปลี่ยน** เจ้าของปิดเองเมื่อพร้อม

เหตุผลที่เป็นหัวข้อแยก ไม่ยัดเข้า `allowances`: `allowances` บังคับว่าทุกคีย์ต้องเป็นตัวเลข
(เหตุการณ์ `morningReviewEnabled` ทำให้ทั้งหน้าเซฟไม่ได้) และต้องอยู่ใน `ALLOWED_APPSETTINGS_KEYS`
กับ `getAppSettings()` และเส้นทางโหลดของเบราว์เซอร์ ไม่งั้นหายไปเงียบๆ (บทเรียนจาก `allowanceRoleRates`)

### 2. ปิดแล้วปฏิเสธทั้งเข้าและออก — ยกเว้นวันที่เริ่มไว้บนเว็บแล้ว

เจ้าของสั่งว่า "ทุกคนสแกนหน้าที่ออฟฟิศ" ⇒ ปฏิเสธทั้งสองทิศทาง · แต่เจ้าของก็สั่งว่าของเก่า
"ใช้ได้ตามปกติ" ⇒ **ถ้าวันนั้นมีเช็กอินผ่านเว็บบันทึกไว้แล้ว ต้องเช็กเอาต์ผ่านเว็บได้**
ไม่งั้นคนที่เช็กอินเว็บไปตอนเช้าแล้วสวิตช์ถูกปิดตอนบ่าย จะปิดวันไม่ได้และเสียสิทธิ์ทั้งวัน

### 3. ไม่แตะ geofence เลย

ตามคำสั่ง · การตรวจว่าต้องมีพิกัดยังทำงานกับทุกการตอกบัตรเหมือนเดิม และรันก่อนสวิตช์นี้

## จุดที่ต้องแก้

| ที่ | ทำอะไร |
|---|---|
| `server.js` `webScanGateReason()` | เพิ่ม reason `web-clock-off` |
| `server.js` ตารางข้อความ fallback | เพิ่มข้อความอังกฤษของ reason ใหม่ |
| `server.js` `DEFAULT_APP_SETTINGS` · `getAppSettings()` · `ALLOWED_APPSETTINGS_KEYS` · รายการ must-be-object · validation | หัวข้อใหม่ต้องผ่านครบทุกด่าน ไม่งั้นเก็บไม่ได้หรือหายเงียบ |
| `app.js` `geofenceUiState()` | บล็อกฝั่งเว็บด้วย reason เดียวกัน |
| `app.js` `geofenceMessage()` + `lang/ja.js` | ข้อความ 3 ภาษา |
| `app.js` เส้นทางโหลด settings | อ่านหัวข้อใหม่กลับมา |
| `app.js` หน้า Settings | สวิตช์ + ติ๊กตำแหน่งที่ยกเว้น |

## เทสต์ที่ต้องมี

1. สวิตช์เปิด (ค่าเริ่มต้น) ⇒ `webScanGateReason` ตอบเหมือนเดิมทุกกรณี — deploy แล้วไม่มีอะไรเปลี่ยน
2. ปิด + ตำแหน่งไม่ถูกยกเว้น ⇒ เช็กอินถูกปฏิเสธด้วย `web-clock-off`
3. ปิด + ตำแหน่งถูกยกเว้น ⇒ ผ่านเหมือนเดิม
4. ปิด + วันนั้นมีเช็กอินผ่านเว็บแล้ว ⇒ เช็กเอาต์ผ่านเว็บยังทำได้
5. การตรวจพิกัดยังมาก่อนสวิตช์เสมอ (ไม่มีพิกัด = ปฏิเสธ ไม่ว่าสวิตช์จะเป็นอะไร)
6. หัวข้อใหม่รอดทั้ง `getAppSettings()` และเส้นทางโหลดของเบราว์เซอร์ (ยามเดียวกับ `allowanceRoleRates`)
7. ฝั่งเว็บกับฝั่ง server ตัดสินตรงกัน

## สิ่งที่จงใจไม่ทำ

- ไม่แตะ geofence ตามคำสั่ง
- ไม่ลบหรือแก้รายการตอกบัตรที่บันทึกไปแล้ว
- ไม่ยุ่งกับเส้นทางคำขอมาเช้า — เจ้าของเคยตอบไว้ว่าเมื่อปิด จะกลายเป็น "มาก่อน 07:30 ได้เงินตามกติกาเดิม"
  ซึ่งเป็นผลที่เกิดเองจากการที่ทุกคนสแกนที่เครื่อง ไม่ต้องเขียนกลไกเพิ่ม
