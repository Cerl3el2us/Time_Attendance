# อัตราเบี้ยเลี้ยง มาเช้า / กลับดึก แยกตามตำแหน่ง — สเปกการออกแบบ

วันที่ 2026-10-13 · เจ้าของสั่ง · สถานะ: รอเจ้าของอ่านก่อนเริ่มลงมือ

## สิ่งที่ต้องได้

เจ้าของได้รับแจ้งว่า **manager ควรได้เบี้ยเลี้ยงมาเช้าและกลับดึกไม่เท่าคนอื่น** ตัวเลขที่ได้รับมาคือ
**360 ทั้งสี่ช่อง** (มาเช้าขั้น 1 และ 2 · กลับดึกขั้น 1 และ 2) ขณะที่คนอื่นได้ 240 / 480

สิ่งที่เจ้าของขอ ไม่ใช่ "ไปแก้เลขให้ manager" แต่คือ:
1. **ปุ่มเปิด/ปิด** การใช้ยอดที่ต่างจากค่ากลาง
2. **ยอดนั้นต้องแก้ไขได้** เผื่อวันหน้ามีการปรับขึ้น
3. มีผล **งวดนี้เป็นต้นไป** ไม่ย้อนหลัง
4. ผูกกับ **ตำแหน่ง (role)** ไม่ใช่รายคน
5. ครอบคลุม **เฉพาะมาเช้ากับกลับดึก** ไม่แตะเบี้ยเลี้ยงประเภทอื่น

**เลข 360 จะไม่ปรากฏในโค้ดเลยแม้แต่เป็นค่าตั้งต้น** — ส่งมอบตารางเปล่าพร้อมสวิตช์ปิด
เจ้าของเป็นคนเปิดสวิตช์และกรอก 360 เองในหน้า Settings (เจ้าของตัดสิน 2026-10-13)
เหตุผล: นโยบายเรื่องเงินต้องอยู่ในข้อมูล ไม่ใช่ในโปรแกรม · ถ้าฝังไว้ เครื่องที่ติดตั้งใหม่จะได้ยอดนั้น
มาเองโดยไม่มีใครสั่ง และวันที่ปรับเป็นเลขอื่นจะมีสองที่ที่บอกไม่ตรงกัน

## สิ่งที่ตรวจพบในโค้ดจริงก่อนออกแบบ (ไม่ใช่การเดา)

| เรื่อง | ความจริง |
|---|---|
| ใครมีสิทธิ์ | `allowanceEligibility.earlyLate` = `md, manager, user, driver` — คุมทั้งมาเช้าและกลับดึกด้วยคีย์เดียว · manager มีสิทธิ์อยู่แล้ว |
| ยอดเงิน | `allowances.earlyMorning1/2` และ `lateNight1/2` — **ค่ากลางค่าเดียวทั้งบริษัท** ไม่มีมิติ role |
| ช่องรายคน | **ไม่มี** ระเบียนพนักงานมีแค่ค่าเดินทาง/ค่าตำแหน่ง/ค่าที่พัก |
| เงินถูกคิดตอนไหน | **ตอนปิดงวด** `server.js` อ่าน `S.allowances.*` ตอนคำนวณ · คำขอเก็บแค่ "ขั้น" ไม่เก็บจำนวนเงิน |
| ทำเป็นตัวคูณได้ไหม | **ไม่ได้** 240→360 คือ ×1.5 แต่ 480→360 คือ ×0.75 ⇒ ต้องเป็นยอดที่กรอกเอง |

## การตัดสินใจเชิงออกแบบ และเหตุผล

### 1. เก็บเป็นหัวข้อใหม่ใน settings ไม่ยัดเข้า `allowances`

```
allowanceRoleRates: {
  enabled: false,
  byRole: { }          // ส่งมอบเปล่า — เจ้าของกรอกเอง
}
```

แต่ละ role ที่กรอกจะได้หน้าตาแบบนี้:

```
byRole: { manager: { earlyMorning1: 360, earlyMorning2: 360, lateNight1: 360, lateNight2: 360 } }
```

**ทำไมไม่ยัดเข้า `allowances`:** `server.js` ตรวจว่าทุกคีย์ใน `allowances` ต้องเป็น **ตัวเลข 0–100000**
ยกเว้นคีย์ที่ลงท้ายด้วย `Enabled` ที่ต้องเป็น boolean · มีคอมเมนต์ในโค้ดบันทึกไว้ว่าเคยมีคนใส่ flag
เข้าไปแล้ว **การเซฟหน้า Settings ทั้งหน้าถูกปฏิเสธทุกครั้ง** จนกว่าจะเพิ่มข้อยกเว้นให้
⇒ การใส่ object ซ้อนจะทำให้เกิดอาการเดิมซ้ำ

**ทำไมเป็นหัวข้อแยก:** `allowanceEligibility` และ `lateDeductPolicy` ก็เป็นหัวข้อแยกที่มี validation
ของตัวเอง ⇒ ทำตามแบบเดิม คนอ่านทีหลังไม่ต้องเรียนรู้วิธีใหม่ และ "role ไหนได้เท่าไร" อ่านออกจาก
ไฟล์ตั้งค่าได้ตรงๆ

**ทางเลือกที่พิจารณาแล้วไม่เอา:** คีย์แบนๆ อย่าง `earlyMorning1_manager` ใน `allowances` เดิม —
ไม่ต้องแตะ validator จริง แต่ทำให้ชื่อคีย์กลายเป็นข้อมูลที่ต้องถอดรหัส และมีเพดาน 50 คีย์รออยู่

### 2. สวิตช์ตัวเดียวคุมทั้งฟีเจอร์

`enabled: false` ⇒ ทุก role กลับไปใช้ค่ากลางทันที **โดยไม่ต้องลบข้อมูลที่กรอกไว้**
role ที่ไม่มีแถวใน `byRole` ⇒ ใช้ค่ากลาง

### 3. ตัวอ่านอัตราตัวเดียว ใช้ทุกที่

```
earlyLateRateFor(role, key, S)   // key = earlyMorning1 | earlyMorning2 | lateNight1 | lateNight2
```

คืนค่า override เมื่อ `enabled` เป็นจริง **และ** role นั้นมีค่าที่ใช้ได้ (เป็นตัวเลขจำกัด ไม่ติดลบ)
นอกนั้นคืนค่ากลางเสมอ — ค่าเสียต้องตกกลับไปที่ค่ากลาง **ห้ามกลายเป็น 0** เพราะ 0 คือการไม่จ่าย

**ฟังก์ชันนี้ต้องมีอยู่ในทั้ง `app.js` และ `server.js` แบบเหมือนกัน** ตามกฎ dual-sync ของโปรเจกต์
(สูตรเงินอยู่สองที่ แก้ที่เดียวแล้วตัวเลขจะแตกกันเงียบๆ) และต้องมีเทสต์ตรึงว่าทั้งสองให้ผลตรงกัน

## จุดที่ต้องแก้ — กวาดจากโค้ดจริงแล้ว

ยอด 4 ตัวนี้ถูกอ่านอยู่ **ประมาณ 15 จุด** ไม่ใช่ 2 จุด

| กลุ่ม | จำนวน | ถ้าตกหล่น จะเกิดอะไร |
|---|---|---|
| เครื่องคิดเงิน `server.js` (ตัวจ่ายจริง) | 5 | **จ่ายผิด** |
| เครื่องคิดเงิน `app.js` (พรีวิว/สลิปบนเว็บ) | 4 | ตัวเลขบนเว็บไม่ตรงกับที่จ่ายจริง |
| ป้าย/ตารางที่โชว์ยอดให้ผู้ใช้เห็น | ~5 | manager เห็น "฿240" แต่ได้จริง 360 ⇒ ดูเหมือนระบบคำนวณผิด |
| ข้อความ FAQ (ไทย/อังกฤษ/ญี่ปุ่น) | 3 บรรทัด | คู่มือบอกเลขผิด |
| หน้า Settings (อ่าน + เซฟ) | 8 | — |

**จุดที่ต้องระวังที่สุด:** จุดที่โชว์ตัวเลข บางที่โชว์ของ "ตัวเอง" บางที่เป็นตารางแอดมินที่โชว์ของคนอื่น
⇒ ต้องส่ง role ของ **เจ้าของแถวนั้น** ไม่ใช่ role ของคนที่กำลังดูหน้าจอ

## หน้า Settings

ใต้กล่อง Allowance Rates เดิม: สวิตช์เปิด/ปิด 1 ตัว + ตาราง (แถว = role · คอลัมน์ = 4 ยอด)
ปิดอยู่ ⇒ ตารางจาง แก้ไม่ได้ · ข้อความครบ 3 ภาษาตามกฎโปรเจกต์
ฝั่ง server ต้องเพิ่มชื่อหัวข้อใหม่เข้ารายการที่อนุญาต 2 จุด และเขียน validation ของตัวเอง
(role ต้องเป็น role ที่รู้จัก · ค่าต้องเป็นตัวเลข 0–100000 เหมือนกฎเดิม · จำกัดจำนวนแถว)

## "งวดนี้เป็นต้นไป" — ได้มาโดยไม่ต้องเขียนกลไกวันที่

payroll คิดเงินตอนปิดงวดจากค่าตั้งค่า ณ ตอนนั้น ⇒ เปลี่ยนค่าวันนี้มีผลกับงวดที่ยังไม่ปิดทั้งงวด
รวมวันที่สแกนไปแล้ว ซึ่งตรงกับที่เจ้าของต้องการพอดี

**เงื่อนไขที่ต้องตรวจก่อนลงมือ:** งวดก่อนหน้าต้องถูกล็อกแล้ว (ระบบมี `PERIOD_LOCKS`)
ถ้ายังไม่ล็อก การเปลี่ยนค่าจะไปเปลี่ยนงวดเก่าด้วย ⇒ **ต้องหยุดถามเจ้าของก่อน ห้ามเดินต่อเอง**

## เทสต์ที่ต้องมี

**เทสต์พิสูจน์กลไก ไม่ใช่พิสูจน์เลข 360** — ใช้ค่าสมมติในเทสต์ เพื่อให้วันที่เจ้าของปรับยอดจริง
ไม่มีเทสต์ไหนแดง (ถ้าเทสต์ปักเลข 360 ไว้ เท่ากับยอดนั้นแก้ไม่ได้จริง ซึ่งขัดกับสิ่งที่ถูกขอ)

1. ปิดสวิตช์ ⇒ ทุก role ได้ค่ากลางเป๊ะ (พิสูจน์ว่าคนที่ไม่เกี่ยวไม่ถูกกระทบ)
2. เปิดสวิตช์ + ตั้งค่าให้ role หนึ่ง ⇒ role นั้นได้ค่าที่ตั้ง · role อื่นยังได้ค่ากลาง
3. **ตัวเลขจาก `app.js` กับ `server.js` ต้องตรงกัน** ด้วยข้อมูลชุดเดียวกัน
4. role ที่ไม่มีแถว / ค่าเสีย (ติดลบ, ไม่ใช่ตัวเลข, ว่าง) ⇒ ตกกลับไปใช้ค่ากลาง **ไม่ใช่ 0**
5. เซฟหน้า Settings ได้ตามปกติหลังมีหัวข้อใหม่ (กันกับดักเดิมที่ทำทั้งหน้าเซฟไม่ได้)
6. ทุกจุดที่โชว์ยอดให้ผู้ใช้เห็น แสดงยอดของ role นั้นจริง ไม่ใช่ค่ากลาง

## สิ่งที่จงใจไม่ทำ

- ไม่ทำ override รายคน — ทุกกฎสิทธิ์ในระบบนี้ผูกกับ role อยู่แล้ว การเพิ่มมิติที่ผูกกับคนจะทำให้มี
  สองวิธีคิดอยู่ในระบบเดียว
- ไม่แตะเบี้ยเลี้ยงประเภทอื่น (upcountry, diligence, long distance, personal car, phone, holiday transport)
  — ยังไม่มีใครขอ และทุกช่องที่เปิดเผื่อคือช่องที่ต้องมีคนตรวจและมีโอกาสตั้งผิด
- ไม่ทำกลไก "มีผลตั้งแต่วันที่" — งวดที่ล็อกแล้วแก้ไม่ได้อยู่แล้ว

## ความเสี่ยงที่รู้ตัว

- **ตกหล่นจุดใดจุดหนึ่งใน ~15 จุด** โดยเฉพาะจุดที่โชว์ตัวเลข — อาการคือ "เลขบนจอไม่ตรงกับสลิป"
  ซึ่งคนใช้จะรายงานว่าระบบคำนวณผิด ⇒ ต้องมีเทสต์ข้อ 6 และต้องกวาดด้วยการค้นหา ไม่ใช่ด้วยความจำ
- **`app.js` กับ `server.js` หลุดจากกัน** ⇒ เทสต์ข้อ 3 เป็นตัวกัน
- **งวดก่อนยังไม่ล็อก** ⇒ ต้องตรวจก่อนลงมือ
