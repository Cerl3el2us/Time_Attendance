# ป๊อปอัป Details ของ Holiday Work: บอกให้ได้ว่า ×2/×3 คือช่วงไหน และไปทำงานที่ไหน

เอกสารออกแบบ · 2026-10-27 · **ยังไม่ได้รับอนุมัติ — ห้ามลงมือแก้ตามเอกสารนี้จนกว่าเจ้าของจะอนุมัติ**

> เจ้าของสั่งเมื่อ 2026-10-27 ว่าให้ **ออกแบบให้จบก่อน แล้วพรุ่งนี้ค่อยเปิด session มาเขียนโค้ด**
> ⇒ เอกสารนี้ต้องอ่านรู้เรื่องโดยไม่ต้องมีบทสนทนาเดิม และต้องพอให้ลงมือได้เลย

## ที่มา

เจ้าของส่งภาพหน้าจอป๊อปอัป **รายละเอียด** ของวันอาทิตย์ที่ 18 ต.ค. 2026 (ผู้ใช้ Toshifumi Takiuchi,
Managing Director) มาพร้อมข้อความ:

> *"ตอนนี้เวลายื่น holiday work มันตรวจสอบข้อมูลได้ไม่ละเอียด ให้ดูจากภาพ มันควรจะกดดูแล้ว เห็นได้ว่า
> พนักงานยื่นขอ ot x2 x3 ตั้งแต่กี่โมง-กี่โมงด้วย **ป้องกันพนักงานแอบยื่นเวลาเกิน** และให้แสดงชื่อสถานที่ๆ
> ไปทำงานด้วย และตอนยื่นขอ holiday work อยากให้มีข้อความบอกด้วยว่า ตรงช่องที่ให้ระบุ **ให้ระบุเวลาทำงาน
> ตามใบ working report**"*

สิ่งที่ป๊อปอัปแสดงอยู่ ณ วันที่เขียน (ตามภาพ):

```
🎌 ทำงานวันหยุด 8 ชม. — รับเป็นเงิน        🚐 ค่าเดินทางวันหยุด (+฿500)
```

เลข `8 ชม.` คือ **ผลบวกของ ×2 กับ ×3 รวมกันเป็นเลขเดียว** และไม่มีทั้งช่วงเวลาและสถานที่
⇒ คนอนุมัติเอาไปเทียบกับใบ working report ไม่ได้ ซึ่งเป็นเหตุผลเดียวที่เปิดป๊อปอัปนี้

## สิ่งที่ตรวจพบก่อนออกแบบ (สำคัญ — ทำให้งานเล็กกว่าที่คิด)

ข้อมูลทุกอย่างที่เจ้าของอยากเห็น **ถูกเก็บครบอยู่แล้ว** ในเรคอร์ดคำขอ ไม่ต้องแก้ฐานข้อมูล ไม่ต้องแก้
เซิร์ฟเวอร์ ไม่ต้อง migrate อะไรเลย — payload ที่ `submitHolidayWork()` ส่ง (`attendance/js/app.js`
บริเวณบรรทัด 21383–21399) มีครบ:

| สิ่งที่เจ้าของขอ | ฟิลด์ที่มีอยู่แล้ว |
|---|---|
| ×2 / ×3 กี่ชั่วโมง | `otHours20`, `otHours30` |
| ตั้งแต่กี่โมงถึงกี่โมง | `workStartTime`, `workEndTime` |
| ชื่อสถานที่ | `locations: [{ name }]` |

และฟังก์ชันช่วยแสดงผลก็มีแล้วบางส่วน:

| ฟังก์ชัน | ที่อยู่ | ทำอะไร |
|---|---|---|
| `holidayWorkTimesLabel(l)` | `app.js:2941` | คืน `07:22–18:22` และต่อท้าย `(วันถัดไป)` ให้เองเมื่อข้ามคืน |
| `otHoursRateDetail(l)` | `app.js:3051` | คืน `7.5 ชม. ×2 + 2.3 ชม. ×3` |
| `splitHolidayWorkOtMinutes()` | `app.js:2502` | ตัวแบ่ง ×2/×3 ตัวจริง (ฝั่งเว็บ) |

**หน้าจัดการคำขอแสดงเวลาอยู่แล้ว** ผ่าน `holidayWorkTimesLabel()` (ใช้ที่ `app.js:16601` และ `18620`)
⇒ **ช่องว่างอยู่ที่ป๊อปอัป Details เท่านั้น** ซึ่งตรงกับภาพที่เจ้าของส่งมาพอดี โค้ดที่ต้องแก้คือบล็อก
`const hwRec = dayLeave('holiday-work')` ที่ `app.js` บริเวณบรรทัด 22625–22640

## กฎการแบ่ง ×2/×3 ที่ต้องเคารพ (อ่านจาก `splitHolidayWorkOtMinutes` ไม่ใช่เดา)

```
stdStart = workSchedule.standardStartHour:standardStartMinute   (ค่าตั้งต้น 08:30)
stdEnd   = 17:30                                                 (ค่าคงที่ในโค้ด)

×3 ท่อนหน้า : [startMin, min(endMin, stdStart))
×2          : [max(startMin, stdStart), min(endMin, stdEnd))  ลบพักเที่ยงเฉพาะส่วนที่ทับ 12:00–13:00
×3 ท่อนหลัง : [max(startMin, stdEnd), endMin)
```

สามเรื่องที่ทำให้ "กี่โมงถึงกี่โมง" **ไม่ใช่ช่วงเดียวเรียบๆ** และต้องออกแบบรองรับ:

1. **×3 มีได้ 2 ท่อน** — ก่อน `stdStart` และหลัง 17:30 (รวมเวลาหลังเที่ยงคืน ซึ่งเป็น ×3 ทั้งหมด)
2. **×2 มีรูโหว่พักเที่ยง** 12:00–13:00 ⇒ แสดงเป็น `08:30–17:30` เฉยๆ จะ**หลอกตา**เพราะชั่วโมงที่จ่ายน้อยกว่า
   ช่วงที่เห็น · เหตุผลที่หักคือค่าแรงรายชั่วโมงคิดจากวันละ 8 ชม. (`salary/30/8`) ⇒ 08:30–17:30 = 8 ชม.
   ไม่ใช่ 9 (เจ้าของตัดสิน 2026-09-23)
3. **กะที่เลิกไม่เกิน 13:00 ไม่ถูกหักพักเที่ยงเลย** — คนนั้นทำงานยาวแล้วกลับบ้าน ไม่เคยได้พัก
   (เจ้าของตัดสิน 2026-10-08) ⇒ ข้อความกำกับต้องไม่โกหกว่าหักทุกกรณี

**โหมด `annual-leave` (แลกวันหยุด) ไม่มี ×2/×3 เลย** — `submitHolidayWork()` ตั้ง
`otSplit = { otHours20: 0, otHours30: 0 }` ตรงๆ โดยไม่เรียกตัวแบ่ง ⇒ บล็อกใหม่ต้องไม่แสดงแถวอัตราในโหมดนี้
แต่ยัง**ต้องแสดงสถานที่และช่วงเวลาที่ยื่น** เพราะคนอนุมัติยังต้องเทียบกับ working report อยู่ดี

## เป้าหมาย

1. คนที่เปิดป๊อปอัป Details ของวันที่มี Holiday Work **เทียบกับใบ working report ได้ทันทีโดยไม่ต้องเปิดหน้าอื่น**
2. เห็นว่า ×2 และ ×3 **แต่ละอัตรากินเวลาช่วงไหน** ไม่ใช่แค่ผลรวมชั่วโมง
3. เห็น**ชื่อสถานที่**ที่ไปทำงาน
4. ตอนยื่น มีข้อความบอกชัดว่า**ให้กรอกเวลาตามใบ working report**
5. ตัวเลขช่วงเวลาที่โชว์ **ต้องตรงกับตัวเลขที่ใช้จ่ายเงินเสมอ** และเพี้ยนเงียบๆ ไม่ได้

## สิ่งที่ไม่ทำ (non-goals)

- **ไม่แตะ `splitHolidayWorkOtMinutes`** ทั้งใน `app.js:2502` และ `server.js:5415` — นั่นคือสูตรเงิน
  และ memory ของโปรเจกต์ (`feedback_attendance_payroll_engine_dual_sync.md`) บันทึกไว้ว่าแก้ที่เดียว
  แล้วตัวเลขแตกกันเงียบๆ · งานนี้เป็น**งานแสดงผลล้วน** ไม่มีเหตุให้แตะฝั่งเงิน
- **ไม่แก้เซิร์ฟเวอร์** ไม่เพิ่มฟิลด์ ไม่เพิ่ม endpoint — ข้อมูลครบแล้ว
- **ไม่เปลี่ยนกฎการคิดเงิน** ไม่ขยับพักเที่ยง ไม่ขยับ 17:30
- **ไม่แก้หน้าจัดการคำขอ** ซึ่งแสดงเวลาอยู่แล้ว — เจ้าของชี้ไปที่ป๊อปอัป Details
- **ไม่เพิ่มการบล็อก/เตือนอัตโนมัติเมื่อเวลาที่ยื่นดูเกินจริง** — เจ้าของขอให้ "มองเห็น" ไม่ได้ขอให้ระบบตัดสิน
  แทนคน · ถ้าจะทำเป็นงานรอบหน้า ต้องถามเกณฑ์ก่อน

## สิ่งที่ถือว่าล้มเหลว (anti-goals)

- **โชว์ `08:30–17:30` โดยไม่บอกว่าหักพักเที่ยง** ⇒ คนอ่านคำนวณเองแล้วได้ 9 ชม. ไม่ตรงกับ 8 ชม. ที่จ่าย
  แล้วคิดว่าระบบคำนวณผิด
- **คำนวณขอบเขตช่วงเวลาขึ้นมาใหม่เองในโค้ดแสดงผล** แล้ววันหนึ่งสูตรเงินเปลี่ยนแต่ตัวแสดงผลไม่เปลี่ยนตาม
  ⇒ หน้าจอโกหกอย่างมั่นใจ · นี่คือความเสี่ยงหลักของงานนี้ ดูหัวข้อ "ยามกันค่าเพี้ยน"
- **ข้อความ 3 ภาษาไม่ครบ** — โปรเจกต์นี้บังคับ TH/EN/JA มาพร้อมกันเสมอ
- **ลืมบัมพ์ cache-buster** แล้วเจ้าของเปิดดูแล้วไม่เห็นอะไรเปลี่ยน

## ส่วนที่ 1 — บล็อกรายละเอียดในป๊อปอัป Details

### หน้าตาที่ต้องการ

```
🎌 ทำงานวันหยุด — รับเป็นเงิน        🚐 ค่าเดินทางวันหยุด (+฿500)
┌────────────────────────────────────────────────┐
│ 📍 สถานที่        โรงงานระยอง                   │
│ 🕐 เวลาที่ยื่น     07:22–18:22                   │
│                                                │
│    ×3   07:22–08:30                   1.13 ชม. │
│    ×2   08:30–17:30 (หักพักเที่ยง)     8.00 ชม. │
│    ×3   17:30–18:22                   0.87 ชม. │
└────────────────────────────────────────────────┘
```

### กฎการแสดง

- **แสดงเฉพาะเมื่อมี `hwRec`** (วันที่มีคำขอ Holiday Work) — วันอื่นไม่มีอะไรเปลี่ยน
- **`📍 สถานที่`** อ่านจาก `hwRec.locations?.[0]?.name` · ถ้าไม่มีหรือว่าง ให้ซ่อนทั้งบรรทัด
  (เรคอร์ดเก่าบางตัวอาจไม่มี — ห้ามโชว์คำว่า `undefined`)
- **`🕐 เวลาที่ยื่น`** ใช้ `holidayWorkTimesLabel(hwRec)` ที่มีอยู่แล้ว ซึ่งจัดการ `(วันถัดไป)` ให้เอง ·
  ถ้าไม่มี `workStartTime`/`workEndTime` ให้ซ่อนทั้งบรรทัดและไม่ต้องแสดงแถวอัตรา
- **แถวอัตรา** แสดงเฉพาะโหมด `paid` · เรียงตามเวลาจริง (×3 ท่อนหน้า → ×2 → ×3 ท่อนหลัง)
  ท่อนที่ยาว 0 นาทีไม่ต้องแสดง
- **วงเล็บ "หักพักเที่ยง"** ต่อท้ายแถว ×2 **เฉพาะเมื่อหักจริง** (`lunchMins > 0`) ตามกฎข้อ 3 ข้างบน
- ตัวเลขชั่วโมงใช้ทศนิยม 2 ตำแหน่งแบบเดียวกับที่ `splitHolidayWorkOtMinutes` ปัดไว้ (`round2`)

### ฟังก์ชันใหม่ที่ต้องเขียน

เขียน **ฟังก์ชันบริสุทธิ์** ตัวเดียวใน `app.js` วางติดกับ `splitHolidayWorkOtMinutes` (บรรทัด ~2502)
เพื่อให้คนอ่านเห็นพร้อมกันว่าทั้งคู่ใช้ขอบเขตชุดเดียวกัน:

```
holidayWorkOtSegments(workStartTime, workEndTime, S)
  → [ { rate: 20|30, startMin, endMin, mins, lunchDeducted: boolean }, ... ]
```

- คืนอาร์เรย์เรียงตามเวลา · ท่อน 0 นาทีถูกคัดออกตั้งแต่ในฟังก์ชัน
- **ห้ามคัดลอกเลข `stdStart`/`stdEnd`/พักเที่ยง มาเขียนซ้ำ** ให้อ่านจากที่เดียวกับตัวแบ่ง
  (ถ้าจำเป็นให้แยกค่าคงที่ออกมาเป็นตัวแปรร่วมในไฟล์เดียวกัน แต่**ยังห้ามแก้ตัวคำนวณเงิน**)
- ฟังก์ชันนี้อยู่ฝั่งเว็บอย่างเดียว ไม่ต้องมีคู่แฝดใน `server.js` เพราะเซิร์ฟเวอร์ไม่ได้แสดงผลอะไร

### ยามกันค่าเพี้ยน (ข้อนี้สำคัญที่สุดของงาน)

เทสต์ต้องพิสูจน์ว่า **ผลรวมนาทีของแต่ละอัตราจาก `holidayWorkOtSegments` เท่ากับ `otMins20`/`otMins30`
ที่ `splitHolidayWorkOtMinutes` คืน** — ไล่หลายอินพุต ไม่ใช่เคสเดียว อย่างน้อย:

| เคส | เหตุผลที่ต้องมี |
|---|---|
| 07:22–18:22 | เคสจากภาพจริงของเจ้าของ มีครบทั้ง 3 ท่อน |
| 09:00–16:00 | อยู่ใน ×2 ล้วน มีพักเที่ยงคร่อม |
| 09:00–12:30 | เลิกก่อน 13:00 ⇒ **ห้ามหักพักเที่ยง** |
| 09:00–13:00 | ขอบพอดีของกฎข้อ 3 |
| 18:00–22:00 | ×3 ล้วน ไม่มี ×2 |
| 06:00–08:00 | ×3 ท่อนหน้าล้วน |
| 20:00–02:00 | ข้ามเที่ยงคืน ⇒ ×3 ทั้งหมด |
| `standardStartHour` ที่ไม่ใช่ 8:30 | พิสูจน์ว่าอ่านจาก settings จริง ไม่ได้ฝังเลข |

ถ้ายามนี้แดง แปลว่าหน้าจอกำลังจะโกหก — **ห้าม merge**

## ส่วนที่ 2 — ข้อความกำกับในฟอร์มยื่นขอ
