# บัญชี superadmin ต้องใช้งานได้เสมอ และกลับมาเองถ้าหาย

**วันที่:** 2026-11-05 · **สถานะ:** อนุมัติแบบแล้ว ยังไม่ลงมือ

## โจทย์จากเจ้าของ (คำของเจ้าของ 2026-11-05)

1. บัญชีนี้จะต้องไม่มีปัญหาในการใช้งาน และหากบัญชีถูกลบไปด้วยความผิดพลาดอะไรสักอย่าง
   บัญชีนี้จะต้องกลับมาได้
2. หากวันข้างหน้าเปลี่ยนคอมเครื่องใหม่ ต้องสามารถใช้งานบัญชีนี้ได้

เจ้าของตัดสินเพิ่มสองข้อ:
- **รหัสผ่าน:** ไม่ได้เก็บไว้ที่ไหนนอกจากในหัวเจ้าของ ("จำได้ ไม่มีทางลืม") ⇒ ระบบไม่ต้องเก็บรหัสจริง
- **วิธีกู้:** ต้อง "กลับเองเงียบๆ" ไม่ต้องให้เจ้าของกดอะไร

## ข้อเท็จจริงที่ตรวจกับโค้ดและเครื่องจริงแล้ว (2026-11-05)

- ผู้อ่าน `SUPERADMIN_PASSWORD` มีที่เดียวในทั้งระบบ: `ensureSystemAccounts()` ใน
  `attendance-server/backend/systemAccount.js:91` และอ่าน **ข้างใน `if (!kept)` เท่านั้น**
  คือเฉพาะตอนไม่มีบัญชี superadmin ใน `users.json`
- บัญชี superadmin มีอยู่จริงบน NAS แล้ว 1 รายการ และมีแฮชรหัสผ่านเก็บไว้
  ⇒ ตัวแปร env ไม่เคยถูกอ่านในสภาพปัจจุบัน
- **ตัวเฝ้า rc.d ไม่ส่ง `SUPERADMIN_PASSWORD` ให้เลย** (`grep SUPERADMIN` ใน
  `/usr/local/etc/rc.d/attendance-autostart.sh` ไม่เจอคำนี้) ⇒ ทุกครั้งที่ตัวเฝ้ากู้ backend
  ซึ่งเป็นวิธีที่ระบบรันมาเป็นเดือน backend รันโดยไม่มีตัวแปรนี้ และไม่มีอะไรพัง
  ⇒ **ความสามารถ "สร้างบัญชีคืนอัตโนมัติ" ที่โจทย์ข้อ 1 ต้องการ วันนี้ยังไม่มีอยู่จริง**
- `ensureSystemAccounts()` ถูกเรียก 3 จุด: `readUsers()` (`server.js:946` — ทุกครั้งที่อ่านไฟล์),
  `saveUsers()` (`server.js:958`) และ bootstrap ตอนสตาร์ต (`server.js:976`)
  ⇒ ถ้ามีแหล่งแฮชให้ใช้ บัญชีจะกลับมาภายในไม่กี่วินาที **ไม่ต้องรีสตาร์ต**
- `express.static` เสิร์ฟเฉพาะโฟลเดอร์หน้าเว็บ (`server.js:9828`) ไม่ได้เสิร์ฟ `backend/data/`
  และไม่มี endpoint ที่ zip หรือไล่อ่านทั้งโฟลเดอร์ `data/` ⇒ ไฟล์ใหม่ใน `data/` ไม่หลุดออกเน็ต
- `atomicWrite(filePath, str, sensitive)` (`server.js:124`) — ส่ง `sensitive: true` เพื่อให้ได้
  สิทธิ์ 600 หลัง rename (ถ้าไม่ส่ง ไฟล์จะกลายเป็น 644 ทุกครั้งที่เขียน)
- `tokenVersion` คือกลไกเพิกถอน token (`server.js:1049`, `1076-1078`): JWT พก `tokenVersion`
  ตอนล็อกอิน ถ้าค่าของผู้ใช้สดไม่ตรงกับใน token จะถูกปฏิเสธ
  ⇒ **การกู้บัญชีคืนด้วย `tokenVersion` ค่าเก่า จะปลุก token ที่เคยถูกเพิกถอนให้ใช้ได้อีก**

## การออกแบบ

### 1. ไฟล์เมล็ด (seed) เก็บเฉพาะแฮช

ไฟล์ใหม่ `${DATA_DIR}/superadmin-seed.json` สิทธิ์ 600 เขียนผ่าน `atomicWrite(..., true)`

```json
{
  "version": 1,
  "password": "<bcrypt hash — ไม่ใช่รหัสจริง>",
  "tokenVersion": 7,
  "mustChangePassword": false,
  "updatedAt": "2026-11-05T09:00:00.000Z"
}
```

**ห้ามมีรหัสผ่านตัวจริงในไฟล์นี้เด็ดขาด** — เก็บแฮชที่ `users.json` ใช้อยู่แล้วเท่านั้น
แฮช bcrypt ย้อนกลับเป็นรหัสจริงไม่ได้ จึงเป็นของที่ยอมให้ไหลเข้า Hyper Backup ได้
ต่างจากรหัสจริง (เรื่องนี้เป็นเหตุที่ไม่เลือกวิธีเก็บรหัสจริงเป็นไฟล์แบบโทเคน Cloudflare)

### 2. ขอบเขตหน้าที่: `systemAccount.js` ไม่แตะดิสก์เอง

`ensureSystemAccounts(users, bcrypt, rounds)` เปลี่ยนเป็น
`ensureSystemAccounts(users, bcrypt, rounds, seedStore)` โดย `seedStore` คือ

```js
{ read() -> object|null,  write(obj) -> void }
```

`server.js` เป็นผู้ให้ตัวจริงที่อ่าน/เขียนไฟล์ · `systemAccount.js` ยังไม่ `require('fs')`
⇒ ทดสอบได้ครบทุกกรณีด้วย seedStore ปลอมในหน่วยความจำ ไม่ต้องแตะดิสก์
และเรียกจาก 3 จุดเดิมได้โดยไม่เปลี่ยนความหมาย · `seedStore` ที่ไม่ส่งมา (undefined) ให้ทำงาน
เหมือนพฤติกรรมเดิมทั้งหมด เพื่อให้เทสต์เก่าและผู้เรียกอื่นไม่พัง

### 3. ตารางพฤติกรรม (ครบทุกกรณี ไม่มีช่องว่าง)

| บัญชีใน users.json | seed | ทำอะไร |
|---|---|---|
| มี | ไม่มี หรือแฮชต่างจากบัญชี | เขียน seed ให้ตรงกับบัญชี · **ไม่แตะ `users.json`** · log `[SYSTEM] superadmin seed updated` |
| มี | แฮชตรงกันแล้ว | ไม่ทำอะไร ไม่เขียนไฟล์ (กัน I/O ทุก request) |
| ไม่มี | มี แฮชใช้ได้ | สร้างบัญชีคืนจากแฮชใน seed · `tokenVersion = seed.tokenVersion + 1` · log `[SYSTEM] Restored superadmin from seed` |
| ไม่มี | ไม่มี แต่มี `SUPERADMIN_PASSWORD` | เหมือนพฤติกรรมเดิม (สร้างจาก env) **แล้วเขียน seed ทันที** |
| ไม่มี | ไม่มี และไม่มี env | เตือนเหมือนเดิม `[SYSTEM] superadmin missing — …` ไม่ล้ม |

**`users.json` ชนะ seed เสมอ** เมื่อทั้งคู่มีแต่ไม่ตรงกัน เพราะบัญชีในไฟล์คือตัวที่ใช้ล็อกอินจริง
(กรณีนี้เกิดได้เมื่อเจ้าของเปลี่ยนรหัสผ่านหน้าเว็บ หรือกู้ `users.json` จากแบ็กอัปเก่า)

**ตัวตัดสินว่าจะเขียน seed ใหม่หรือไม่ คือฟิลด์ `password` เท่านั้น** (เทียบสตริงแฮชตรงๆ)
ไม่เอา `tokenVersion` หรือ `mustChangePassword` มาร่วมตัดสิน เพราะจะทำให้เกิดการเขียนไฟล์
บ่อยโดยไม่ได้ประโยชน์ · แต่เมื่อถึงคราวต้องเขียน ให้เขียนทั้งสามฟิลด์จากค่าที่บัญชีมีอยู่
ณ ขณะนั้น พร้อม `updatedAt` ใหม่

**`tokenVersion = seed.tokenVersion + 1`** เป็นข้อบังคับ ไม่ใช่ทางเลือก: การคืนค่าเก่าตรงๆ
จะทำให้ token ที่เคยถูกเพิกถอนด้วยการเปลี่ยนรหัสผ่านกลับมาใช้ได้อีก การบวกหนึ่งรับประกันว่า
token ทุกใบที่ออกไปก่อนหน้าใช้ไม่ได้ · ราคาที่จ่ายคือถ้าบัญชีหายตอนที่กำลังล็อกอินอยู่
จะถูกเด้งออกและต้องล็อกอินใหม่ ซึ่งยอมรับได้และปลอดภัยกว่า

### 4. ความทนทานต่อความผิดพลาด

`readUsers()` ถูกเรียกแทบทุก request ⇒ **โค้ดส่วนนี้ห้าม throw ออกไปข้างนอกเด็ดขาด**

- seed อ่านไม่ออก / JSON พัง / `version` ไม่ใช่ 1 / ไม่มีฟิลด์ `password`
  → ถือว่า "ไม่มี seed" · log `[SYSTEM] superadmin seed unreadable — ignoring` ระดับ error
  · **ไม่ลบและไม่ทับไฟล์เดิม** เก็บไว้ให้คนไปดู (ยกเว้นกรณีที่ตารางสั่งให้เขียนทับเพราะบัญชีมีอยู่)
- เขียน seed ไม่สำเร็จ (สิทธิ์ / ดิสก์เต็ม) → log error แล้วไปต่อ · การอ่าน users ต้องสำเร็จเหมือนเดิม
- แฮชใน seed ต้องมีรูปร่างเป็น bcrypt (`$2a$` / `$2b$` / `$2y$` ขึ้นต้น) ไม่ใช่สตริงอะไรก็ได้
  → ถ้าไม่ผ่าน ถือว่า "ไม่มี seed" เพื่อกันการเขียนบัญชีที่ล็อกอินไม่ได้ลงไฟล์

### 5. เลิกส่งรหัสผ่านทางบรรทัดคำสั่ง

ถอด `env_prefix` ออกจาก `start_sh` ใน `attendance-server/scripts/deploy/deploy_backend.py`
(และถอด `env_bits` / การอ่าน `SUPERADMIN_PASSWORD` จาก env ของเครื่อง ออกทั้งชุด)

**การเปลี่ยนนี้อยู่ในสคริปต์ deploy เท่านั้น** — ฝั่ง `server.js` / `systemAccount.js`
**ยังอ่าน `process.env.SUPERADMIN_PASSWORD` ต่อเหมือนเดิม** ตามแถวที่ 4 ของตารางพฤติกรรม
เพื่อให้ทางติดตั้งใหม่หมดยังทำงานได้ · ที่เลิกทำคือ "สคริปต์ deploy หยิบรหัสจากเครื่องของคน
ไปแปะบนบรรทัดคำสั่งบน NAS ทุกครั้งที่ deploy" ซึ่งเป็นต้นเหตุที่รหัสโผล่ใน `ps`

เหตุผล: เมื่อมี seed บน NAS แล้ว ตัวแปรนี้ไม่มีหน้าที่อะไรในการใช้งานประจำวันอีก และการส่งมันไป
ทำให้รหัสโผล่เป็นข้อความเปิดใน `ps aux` บน NAS (พบ 2026-11-05 — เชลล์ห่อ `sh -c` ค้างอยู่ถาวร
หลังคอมมิต `1380ccd` เพราะไม่มี pty ให้รื้อ ⇒ หน้าต่างเปิดเผยยาวจนถึงรีสตาร์ตรอบถัดไป)

**ทางติดตั้งใหม่หมด** (ไม่มีทั้งบัญชีและ seed เช่น NAS เครื่องใหม่): ไม่ทำเป็นฟีเจอร์ในสคริปต์
deploy เพราะเป็นเหตุการณ์ที่เกิดครั้งเดียวและมีทางอื่นอยู่แล้ว ⇒ เขียนวิธีไว้ใน
`DEVELOPER_HANDOFF.md` ว่าให้ตั้ง `SUPERADMIN_PASSWORD` ชั่วคราวในสคริปต์ rc.d บน NAS
หรือรัน backend ด้วยมือหนึ่งรอบ แล้วลบออก · โจทย์ข้อ 2 ของเจ้าของไม่ได้พึ่งทางนี้
เพราะ seed อยู่บน NAS ไม่ได้อยู่ในคอม

### 6. สิ่งที่ตั้งใจไม่ทำในรอบนี้ (YAGNI)

- **ไม่เปลี่ยนรูปคำสั่ง start เป็น `setsid --fork`** แม้จะวัดแล้วว่าได้โปรเซสเดียวสะอาดกว่า
  (ปัจจุบันเชลล์ห่อค้างทำให้ `FIND_PID` นับได้ 2 pid) เพราะรูป `nohup … &` เพิ่งพิสูจน์บนของจริง
  เมื่อ 2026-11-05 09:41 ว่าใช้ได้ และการเปลี่ยนต้องแลกด้วยการรีสตาร์ตเพื่อพิสูจน์อีกรอบ
  ⇒ เก็บเป็นข้อแยกใน `STATUS.md` ไม่รวมในงานนี้
- ไม่ทำ UI สำหรับกู้บัญชี ไม่ทำการแจ้งเตือนเมื่อกู้ (log พอ — เจ้าของเลือก "เงียบๆ")
- ไม่เก็บประวัติแฮชย้อนหลัง เก็บค่าปัจจุบันค่าเดียว

## การทดสอบ

ไฟล์ใหม่ `tests/superadmin-seed.test.js` ใช้ seedStore ปลอมในหน่วยความจำ ครอบทั้ง 5 แถว
ของตารางพฤติกรรม บวกกรณีผิดพลาด:

1. บัญชีมี + ไม่มี seed → เขียน seed ตรงกับบัญชี และ `users.json` ไม่ถูกแก้
2. บัญชีมี + seed ตรงแล้ว → ไม่มีการเขียนไฟล์เลย
3. บัญชีมี + seed แฮชเก่า (จำลองการเปลี่ยนรหัสหน้าเว็บ) → seed ถูกอัปเดต บัญชีไม่ถูกแตะ
4. บัญชีหาย + seed ใช้ได้ → บัญชีกลับมา แฮชตรงกับ seed และ **`tokenVersion` มากกว่าใน seed 1**
5. บัญชีหาย + ไม่มี seed + มี env → สร้างจาก env และเขียน seed
6. บัญชีหาย + ไม่มี seed + ไม่มี env → เตือน ไม่สร้าง ไม่ throw
7. seed JSON พัง / `version` ผิด / แฮชไม่ใช่รูป bcrypt → ถือว่าไม่มี seed ไม่ throw ไม่ลบไฟล์
8. `seedStore.write()` โยน error → `ensureSystemAccounts` ยังคืนผู้ใช้ได้ปกติ
9. ไม่ส่ง `seedStore` มาเลย → พฤติกรรมเหมือนเดิมทุกอย่าง (กันเทสต์เก่าพัง)

แก้ยามเดิม `tests/deploy-starts-as-root.test.js:54` ที่บังคับว่า start ต้องมี `env_prefix`
ให้กลับด้านเป็น **ต้องไม่มี** `SUPERADMIN_PASSWORD` หรือ `env_prefix` ในคำสั่ง start
พร้อมคอมเมนต์อ้างเหตุผลข้อ 5

สิ่งที่เทสต์พิสูจน์ไม่ได้และต้องตรวจบนของจริงหลัง deploy: สิทธิ์ไฟล์ seed เป็น 600 จริง
และ log `[SYSTEM] superadmin seed updated` ขึ้นจริงหนึ่งครั้งหลังสตาร์ต

รหัส superadmin ตัวปัจจุบันเคยปรากฏใน `ps aux` บน NAS และหลุดเข้าบันทึกแชตเมื่อ 2026-11-05
⇒ ควรเปลี่ยนรหัสผ่านที่หน้าเว็บ (Profile → Change Password) ซึ่งทำได้ทันทีโดยไม่ต้องรอสเปกนี้
และกลไก seed จะตามแฮชใหม่ให้เองในการอ่าน `users.json` ครั้งถัดไป
