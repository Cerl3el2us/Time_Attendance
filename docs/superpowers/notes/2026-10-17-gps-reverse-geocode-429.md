# ที่อยู่ของลิงก์ GPS ไม่เคยขึ้นบนเว็บจริง — Nominatim ตอบ 429 ให้ IP ออฟฟิศ — 2026-10-17

อาการที่เห็น: ช่องที่อยู่ของลิงก์ GPS ในหน้า "ตารางเวลาทำงาน" แสดงแต่พิกัดดิบ
(`13.724704, 100.550299`) ไม่เคยกลายเป็นชื่อสถานที่ · console เต็มไปด้วยคู่ error
"CORS blocked" + "net::ERR_FAILED" ของ `https://nominatim.openstreetmap.org/reverse`

## ต้นตอชั้นที่ 1 — Nominatim ปฏิเสธเพราะ rate limit ไม่ใช่เพราะ CORS และไม่ใช่เพราะ User-Agent

วัดจากเครื่องออฟฟิศ (`tairo`, ออก IP เดียวกับที่เบราว์เซอร์ของพนักงานใช้) ด้วย `curl` ซึ่งเห็น
HTTP status จริง — สิ่งที่เบราว์เซอร์ซ่อนไว้เบื้องหลังคำว่า CORS:

| คำขอ | ผล |
|---|---|
| `/reverse?...&accept-language=th` (URL เดียวกับที่แอปยิง) | **HTTP 429 Too many requests** |
| คำขอเดิม + `User-Agent` ที่ระบุตัวตน | **429** |
| คำขอเดิม + `Origin: https://attendance.tozaiboeki.co.th` | **429** |
| คำขอเดิม + UA แบบเบราว์เซอร์ + `Origin` | **429** |
| `/status.php` (นาทีเดียวกัน IP เดียวกัน) | **200** |
| `/reverse` พิกัดอื่น (โตเกียว / ซูริก / ป่าอะเมซอน) | **429** (มีช่วงที่หลุดมา 200 ได้บ้าง) |

สรุปจากตารางนี้:

1. **บริการไม่ได้ล่ม** — `status.php` ตอบ 200 จาก IP เดียวกันในนาทีเดียวกัน
2. **ไม่ใช่เพราะไม่มี User-Agent ระบุตัวตน** — ใส่แล้วก็ยัง 429 ⇒ การเติม UA แก้ไม่ได้
   (และ `fetch()` ในเบราว์เซอร์ตั้ง `User-Agent` เองไม่ได้อยู่แล้ว)
3. **ไม่ใช่ปัญหา CSP** — `attendance/index.html` อนุญาต `https://nominatim.openstreetmap.org`
   ใน `connect-src` อยู่แล้วตั้งแต่ 2026-09-24 ⇒ ไม่ต้องแตะ CSP
4. **ที่เบราว์เซอร์เรียกว่า CORS error คือหน้า 429** — หน้า error ของ Varnish ไม่ส่ง header
   `Access-Control-Allow-Origin` มาด้วย (หน้า 200 ส่ง) ⇒ เบราว์เซอร์จึงบล็อกแล้วรายงานว่าเป็น
   เรื่อง CORS ทั้งที่ความจริงคือถูกจำกัดอัตรา · **อ่าน error ตามตัวอักษรแล้วจะแก้ผิดจุด**
5. 429 ที่ได้มาเป็น `X-Cache: MISS` ทุกใบ และยิงซ้ำ 6 ครั้งห่างกัน 10 วินาทีก็ยัง 429 ทุกครั้ง
   ⇒ ไม่ใช่แค่ "ยิงเร็วเกินในวินาทีนั้น" แต่เป็นสภาพที่ IP นี้ถูกจำกัดอยู่เป็นปกติ

เทียบกับนโยบายการใช้งานของ Nominatim (บริการฟรีที่ OSM ออกค่าใช้จ่ายให้): สูงสุด 1 คำขอ/วินาที
ห้ามใช้แบบ heavy use และห้ามทำ bulk geocoding — ซึ่งตรงกับพฤติกรรมของแอปในชั้นที่ 2 ข้างล่าง

## ต้นตอชั้นที่ 2 — แอปยิงซ้ำไม่มีที่สิ้นสุด เพราะ cache เก็บแต่เคสที่สำเร็จ

`reverseGeocode()` ใน `attendance/js/app.js` เขียน `geoCache[key]` อยู่ **ข้างใน `.then()`**
ส่วน `.catch()` เรียก callback กลับไปเฉยๆ โดยไม่บันทึกว่าพิกัดนี้เพิ่งล้มเหลว
⇒ เมื่อทุกคำขอถูกปฏิเสธ `geoCache` จึงว่างตลอดกาล และทุกการ render ก็เริ่มนับหนึ่งใหม่

วัดบนเว็บจริง 2026-10-17 (ล็อกอิน role `md` ด้วยบัญชี QA ที่เจ้าของให้ไว้, เบราว์เซอร์ในแอป,
ครอบ `window.fetch` เพื่อนับคำขอ):

- ลิงก์ GPS ใน DOM: **12 ลิงก์** (แถวตารางเดสก์ท็อปกับการ์ดมือถือถูก render ทั้งคู่เสมอ)
- พิกัดที่ไม่ซ้ำ (ปัดทศนิยม 4 ตำแหน่ง ≈ 11 ม.): **5 พิกัด**
- คำขอที่ยิงออกไปจริงต่อการ render 1 ครั้ง: **5 คำขอ** ⇒ การ dedupe ต่อ render *ทำงานถูกอยู่แล้ว*
  (ถูกแก้ไว้เมื่อ 2026-08-17) — ไม่ใช่จุดที่พัง
- ปล่อยหน้าไว้เฉยๆ 10 วินาที: **+0 คำขอ** ⇒ ไม่มี timer หรือ WS ที่ re-render เอง
- เรียก `renderAttendanceTable()` ซ้ำ: **+5 คำขอทุกครั้ง** URL เดิมทั้ง 5 และ `geoCache` ยังว่าง (0 คีย์)

⇒ ตัวคูณที่ทำให้ console มี error เป็นร้อยคือ **จำนวนครั้งที่ re-render × 5** ไม่ใช่การยิงพร้อมกัน
รอบเดียว · หน้าเดียวกัน re-render บ่อยมาก: สลับเดือน สลับพนักงาน (md เลือกได้ทุกคน) สลับภาษา
(`applyLanguage()` เรียก `navigateTo()`) และทุกครั้งที่กลับเข้าหน้านี้

### จุดที่คิวยังไม่คุม

- `geocodeTableGpsLinks()` หน่วงด้วย `setTimeout(..., i * 1100)` โดย `i` เริ่มนับ 0 ใหม่ทุกครั้งที่
  ถูกเรียก ⇒ render สองครั้งห่างกัน 1 วินาที ทำให้คำขอของรอบใหม่ไปทับเวลาของรอบเก่า
- ตัวเรียกอีกจุด (ป๊อปอัป Details, `renderGpsEntry()`) เรียก `reverseGeocode()` **ทันที** ไม่ผ่าน
  การหน่วงใดๆ ⇒ เปิดป๊อปอัปขณะตารางกำลังทยอยยิง ก็เกิน 1 คำขอ/วินาทีอยู่ดี

⇒ การหน่วงที่กระจายอยู่ตามจุดเรียก เอาไปรวมเป็น **คิวเดียวของทั้งแอป** ได้ประโยชน์กว่า

## สิ่งที่เจ้าของตัดสิน 2026-10-17 — เลิกแปลง

ตอนแรกผมเสนอให้ย้ายไปให้ backend แปลงแล้ว cache ถาวร เจ้าของถามกลับสั้นๆ ว่า **"แปลงทำไม
ทำไมต้องแปลง"** ซึ่งเป็นคำถามที่ถูกกว่าข้อเสนอของผม พอไปตรวจจึงพบว่า:

1. **ไม่เคยมีใครตัดสินใจว่าต้องแปลง** — `reverseGeocode()` มากับ commit แรกของ repo
   (`33e1994`, 2026-08-31) พร้อมโค้ดชุดเดิม ไม่มีสเปก ไม่มีบันทึกว่าใครสั่ง ไม่มีเหตุผลเขียนไว้ที่ไหน
2. **ไม่มีกฎธุรกิจข้อไหนอ่านที่อยู่เลย** — ตัวที่ตัดสินจริงคือ geofence ฝั่ง server ซึ่งคิดจากพิกัดดิบ
   กับระยะทาง · ลบที่อยู่ทิ้งแล้วไม่มีกฎข้อไหนเปลี่ยน ไม่มีตัวเลขเงินข้อไหนขยับ
3. **ข้อมูลครบอยู่แล้วโดยไม่ต้องแปลง** — ลิงก์ Google Maps ที่พิกัดนั้น, พิกัดเต็ม 6 ตำแหน่ง,
   และค่าความแม่น ±เมตร · สิ่งเดียวที่การแปลงให้เพิ่มคือกวาดตาดูทั้งเดือนรวดเดียวโดยไม่ต้องกดลิงก์
4. ต้นทุนคือพิกัดพนักงานออกไปหา OpenStreetMap ทุกครั้งที่ render

⇒ **ลบทั้งชุด** (`reverseGeocode`, คิว, cache ทั้งหมด, คีย์ `ja.js` ของข้อความ "แปลงไม่ได้",
หมุด Nominatim ใน `tests/superadmin-reach.test.js` และ host ใน CSP ของ `attendance/index.html`)
เหลือ `gpsCoordsLabel()` บรรทัดเดียวที่เติมคำว่า `พิกัด` / `coords` / `座標` หน้าตัวเลข เพื่อไม่ให้
อ่านตัวเลขเป็นชื่อสถานที่ · ตอนนี้ `loadGpsCartoStyle()` เป็น fetch ตัวเดียวใน `app.js` ที่ออกนอกองค์กร

**บทเรียนที่อยากให้รอบหน้าได้ไป:** ผมใช้เวลาไปกับการทำให้ของที่พังทำงานได้ ก่อนจะถามว่าของนั้น
มีไว้ทำไม · งานที่ส่งมอบจริงมีโค้ดน้อยกว่าทั้งของเดิมและของที่ผมเขียนรอบแรก
