# กวาดหาค่าตั้งต้นที่กลืนเลข 0 ของเบี้ยเลี้ยง — 2026-10-16

สิ่งที่ทำ: ดึงทุกจุดที่เขียนว่า `allowances.<คีย์> || <ค่าตั้งต้น>` ออกจาก `attendance/js/app.js`
และ `attendance-server/backend/server.js` **โดยตัดบรรทัดคอมเมนต์ทิ้งก่อน** แล้วเทียบว่าฝั่งแสดงผล
กับฝั่งจ่ายเงินตกลงกันไหมว่า "ไม่ได้ตั้งค่า" กับ "ตั้งเป็น 0" แปลว่าอะไร

ที่ต้องตัดคอมเมนต์ก่อนเพราะรอบแรกที่ไม่ตัด ได้ผลบวกลวง 2 ตัวจาก 3:
`server.js` มี `S.allowances.personalCar || 1000` อยู่ใน**คอมเมนต์**ที่บันทึกว่าแก้ไปแล้วเมื่อ
2026-07-31 และ `LONG_DISTANCE_THRESHOLD_KM` ก็คือเลข 250 ตัวเดียวกับที่ `server.js` ใช้
⇒ การจับข้อความอย่างเดียวบอกไม่ได้ว่าอะไรเป็นโค้ดจริง (บทเรียนเดิม: การจับข้อความไม่ใช่ความครบถ้วน)

## แก้ไปแล้วในรอบนี้

- **Long Distance** — ฝั่งแสดงผลใช้ `|| 150` ฝั่งจ่ายใช้ `|| 0` ⇒ ตั้งอัตราเป็น 0 แล้วฟอร์มยังบอก
  คนขับว่า "+฿150/วัน" ส่วนคำขอที่เซิร์ฟเวอร์สร้างถือ ฿0 · แก้ด้วย `longDistanceRateOf()`
  และมี `tests/long-distance-rate-display.test.js` คุม
- **FAQ รถส่วนตัว** — `|| 1000` ใน 3 ภาษา ⇒ ตั้งอัตราเป็น 0 แล้ว FAQ ยังบอก "฿1,000 ต่อครั้ง"
  ทั้งที่ปุ่มขอถูกซ่อนและไม่มีการจ่าย · จุดที่ตัดสินเงินถูกต้องอยู่แล้วทุกจุด

## รับรู้แล้ว แต่เลือกไม่แก้ — เกณฑ์เวลามาเช้าเมื่อตั้งเป็น 0

`app.js` อ่านเกณฑ์แบบมีค่าตั้งต้นอยู่ 2 จุด — `earlyMorningThresholdMins()` ใช้
`S.earlyThreshold2Min || 390` / `S.earlyThreshold1Min || 450` และอีกจุดใช้
`Number.isFinite(...) ? ... : 450` — ส่วน `server.js` อ่านค่าดิบล้วนทุกจุดที่ตัดสิน
(`mins <= S.allowances.earlyThreshold2Min`)

**ผลถ้าเจ้าของตั้งเกณฑ์เป็น 0** (ความหมายที่น่าจะตั้งใจ: ปิด tier นั้น ไม่ให้ใครผ่าน):
ฝั่งเบราว์เซอร์จะกลับไปใช้ 390/450 ⇒ ฟอร์มยอมให้เลือก tier นั้น แต่เซิร์ฟเวอร์เทียบกับ 0
แล้วปฏิเสธด้วย 400 ⇒ พนักงานกดส่งแล้วโดนปฏิเสธโดยไม่เข้าใจว่าทำไม

**ทำไมไม่แก้ตอนนี้:** ช่องแคบ ต้องตั้งเกณฑ์เป็น 0 ซึ่งยังไม่เคยเกิด และทั้งสองเอนจินเขียนค่าตั้งต้น
450/390 ลงไฟล์ตั้งค่าตอนสร้าง ⇒ กรณี "ไม่มีคีย์" แทบเป็นไปไม่ได้ · ที่สำคัญกว่าคือ **ยังไม่ได้
ทดลองของจริง** ว่าเซิร์ฟเวอร์ตอบ 400 จริงตามที่อ่านจากโค้ด — ถ้าจะแก้ ต้องพิสูจน์ก่อน ไม่ใช่แก้
ตามที่เดา

**ถ้าจะหยิบขึ้นมาทำ:** ให้ทั้งสองฝั่งอ่านผ่านตัวอ่านตัวเดียวแบบ `!= null ?` เหมือนที่
`longDistanceRateOf()` ทำ แล้วเพิ่มเคสเกณฑ์ = 0 เข้า `tests/long-distance-rate-display.test.js`
หรือไฟล์เทสต์ของมันเอง

## รอบตรวจด้วยบัญชี accounting บนข้อมูลจริง — 2026-10-16 (ไม่เจอบั๊กใหม่)

เจ้าของล็อกอิน `accounting` ค้างไว้ให้ แล้วสั่งให้เน้นหน้า Settings กับคิวอนุมัติ
**ทุกอย่างด้านล่างอ่านอย่างเดียว ไม่ได้กดบันทึกค่าตั้งค่าใดๆ** เพราะการเซฟกระทบผู้ใช้ทุกคน

| ตรวจอะไร | วิธี | ผล |
|---|---|---|
| ช่องตัวเลขในหน้า Settings | เทียบค่าที่ฟอร์มแสดงกับ `APP_SETTINGS` ทีละช่อง | ตรงกันทุกช่องที่มีอยู่ |
| ตารางอัตรารายตำแหน่ง | เทียบแถวที่เรนเดอร์กับตำแหน่งที่มีสิทธิ์ `earlyLate` | แถว = ตำแหน่งที่มีสิทธิ์ (manager, user) ถูกต้อง |
| ดรอปดาวน์ "เพิ่มตำแหน่ง" | ตรวจว่าทำไมไม่แสดง | `_addable` ว่าง เพราะตำแหน่งที่มีสิทธิ์มีแถวครบแล้ว — ตั้งใจ |
| ตัวกรองคิวอนุมัติ | ยิง `isMyTurnNow()` ด้วย 12 ประเภท × 6 สถานะ | บัญชีเห็นเฉพาะ `pending-accounting` เท่านั้น ไม่หลุด |
| เมนูเข้าคิวอนุมัติ | ดู sidebar ของ accounting จริง | มี "✅ จัดการคำขอ" อยู่แล้ว |
| **หน้า Finalize Payroll** | เทียบยอดรวมรายได้ที่พิมพ์ กับ `computePayroll()` ทั้ง 9 คน | **ตรงกันทุกคน ไม่คลาดแม้แต่สตางค์** |
| ป๊อปอัป Details vs สลิป | วันที่มี Holiday Work จริง | ตรงกันทุกตัวเลข (บันทึกไว้ใน `STATUS_CLOSED.md`) |

### สองเรื่องที่ดูเหมือนบั๊กแต่ไม่ใช่ — อย่าเสียเวลาไล่ซ้ำ

- **ตารางอัตรารายตำแหน่งมีแค่ 2 ตำแหน่ง** จาก 6 — เพราะอีก 4 ตำแหน่งปิดสิทธิ์ `earlyLate` ไว้
  ไม่ใช่ตารางพัง · โค้ดมีโน้ตว่าเจ้าของเคยสับสนเรื่องนี้เมื่อ 2026-10-14 แล้วเพิ่มคำอธิบายที่มา
  ของรายชื่อไว้แล้ว
- **เมนู "ใบเงินเดือน" ซ้ำสองอัน** — ตั้งใจ: `nav-emp-only` สำหรับพนักงาน และ `nav-admin`
  สำหรับผู้ดูแล ระบบซ่อนตัวที่ไม่ตรง role
