# รีวิวรอบ 5 ของงาน Holiday Work — ข้อที่ไล่แล้ว "ไม่แก้" และเหตุผล (2026-10-28)

ข้อที่แก้แล้วอยู่ใน `git log` (`6e347bc`, `10b732b` และก่อนหน้า) ไฟล์นี้เก็บเฉพาะข้อที่ **ตั้งใจไม่แก้**
พร้อมเงื่อนไขที่จะทำให้ต้องกลับมาแก้ เพื่อไม่ให้รอบหน้าเสียเวลาไล่ซ้ำ แล้วสรุปเหมือนกันอีกครั้ง

เรื่องที่กระทบเงินบนหน้า Reports / Dashboard / สรุปงวด **ไม่ได้อยู่ในไฟล์นี้** — มันอยู่ใน
`STATUS.md` หัวข้อ `## เปิดอยู่` เพราะต้องให้เจ้าของตัดสิน

## 1. `holidayWorkLocationLabel()` อ่านแค่ `locations[0]` ขณะที่ `hasUpcountryLocation()` ใช้ `.some()`

เรคอร์ดหน้าตา `locations: [{name:''},{name:'NGK'}]` จะได้ 🗺️ และได้ ฿240 (เพราะ `.some()` เจอชื่อ
ในรายการที่สอง) แต่บรรทัด 📍 สถานที่ในบล็อกรายละเอียดจะเงียบ เพราะมันอ่านแต่ตัวแรกที่ชื่อว่าง

**ไม่แก้เพราะ:** ข้อมูลใหม่และข้อมูลที่แก้ไขสร้างรูปนี้ไม่ได้เลย — `validateHolidayWorkLocation()`
ยอมรับเฉพาะ "ไม่มีสถานที่" หรือ "มีรายการเดียวที่มีชื่อ" และบังคับทั้ง POST และ PUT (ไล่จุดเรียก
ครบแล้ว มีด่านอยู่ทั้งสองทาง) ⇒ เหลือความเป็นไปได้แค่เรคอร์ดเก่าก่อนมีตัวตรวจ ซึ่งในข้อมูลจริง
วันนี้ไม่มีสักใบ (ไล่ทั้ง 5 ใบที่อนุมัติแล้ว ทุกใบมี `locations` ยาว 0 หรือ 1)

**จะต้องกลับมาแก้เมื่อ:** ตัวตรวจถูกผ่อนให้รับหลายสถานที่ (เช่น ให้แวะหลายแห่งในวันหยุดได้)
ถ้าถึงวันนั้น ให้ `holidayWorkLocationLabel()` ใช้ `.filter(ชื่อไม่ว่าง)` แล้วต่อด้วยคั่นจุด
แบบเดียวกับที่หน้า Upcountry ทำอยู่ ไม่ใช่อ่านตัวแรกตัวเดียว

## 2. ตอนแก้ใบที่มีไฟล์ Working Report อยู่แล้ว ดอกจันแดงกับคำว่า "ยังไม่ได้เลือกไฟล์" ขัดกัน

เปิดแก้ใบที่มีสถานที่อยู่แล้ว ⇒ ช่องสถานที่ถูกเติมให้ ⇒ `refreshHolidayWorkPayCompare()` โชว์
ดอกจันแดงที่ Working Report (ถูกต้องตามกฎ "กรอกสถานที่แล้วต้องแนบ") แต่ชื่อไฟล์ใต้ปุ่มยังเขียนว่า
"ยังไม่ได้เลือกไฟล์" เพราะผู้ใช้ยังไม่ได้เลือกไฟล์ *ใหม่* · กดยื่นได้ปกติ เพราะทั้งฝั่งเว็บและเซิร์ฟเวอร์
ดูไฟล์ที่เก็บไว้เดิม (`_hwStoredFile` / `resolvedAttachment`) ไม่ใช่ดูว่ามีไฟล์ใหม่ไหม

**ไม่แก้เพราะ:** ไม่ใช่ของใหม่และไม่ใช่บั๊กที่ทำอะไรผิด — ก่อนงานนี้ดอกจันติดอยู่ถาวรด้วยซ้ำ
จึงขัดกับข้อความนั้นตลอดเวลา · การแก้ที่ถูกคือเอาชื่อไฟล์เดิมมาแสดงแทนคำว่า "ยังไม่ได้เลือกไฟล์"
ซึ่งเป็นงานหน้าตา ไม่ใช่งานเงิน และรอบนี้เป็นรอบแก้บั๊กเงิน ⇒ ไม่ขยายขอบเขตเอง
(เทียบเคียง: เรื่องคอนทราสต์ปุ่มที่เจ้าของสั่งว่า "ปล่อยไว้ก่อน" เมื่อ 2026-10-28)

**ถ้าจะทำ:** `#holiday-work-file-name` ควรอ่านชื่อไฟล์จากเรคอร์ดที่กำลังแก้เมื่อยังไม่มีไฟล์ใหม่
และเขียนให้ชัดว่า "ใช้ไฟล์เดิม: <ชื่อ>" พร้อมข้อความ 3 ภาษาตามกฎของโปรเจกต์

## รอบ 6 — ข้อที่ไล่แล้วไม่แก้ (เรื่องใหญ่สองกลุ่มไปอยู่ `STATUS.md` รอเจ้าของตัดสิน)

### ก. หัวกระดาษอาจเป็นชื่อคนที่กำลังดู แม้ไอคอนเบี้ยจะถูกคนแล้ว

รอบ 6 แก้ให้ทุกการค้นเรคอร์ดในใบพิมพ์ใช้ `ownerUserId` แล้ว แต่ `targetUser.name` /
`targetUser.employeeNo` ที่พิมพ์บนหัวเอกสารยังมาจาก `targetUser` ตัวเดิม ⇒ เมื่อหาเจ้าของใน
`DATA_USERS` ไม่เจอ **ตารางและไอคอนเป็นของเจ้าของ แต่ชื่อบนหัวเป็นของคนที่กำลังดู**

**ไม่แก้เพราะ:** `targetUser` ถอยไปเป็น `currentUser` เป็นพฤติกรรมของ **ทั้งหน้า** attendance
(หัวตารางบนจอก็ใช้ตัวเดียวกัน) ไม่ใช่ของใบพิมพ์ · การแก้ที่ถูกคือตัดสินใจว่าเมื่อหาเจ้าของไม่เจอ
หน้านี้ควรทำอะไร (ไม่เรนเดอร์เลย / ขึ้นว่าไม่ทราบชื่อ / ใช้ id) ซึ่งเป็นการออกแบบ ไม่ใช่การแก้บั๊ก
และกระทบทุกส่วนของหน้า ⇒ นอกขอบเขตของการแก้บั๊กเงิน

**เกิดได้เมื่อ:** พนักงานถูกลบหรือปิดใช้งานระหว่างที่หน้าเปิดค้างอยู่ (ดู
[[feedback-attendance-stale-open-page]]) · หลังรอบ 6 ความเสียหายลดจาก "เบี้ยผิดคน" เหลือ
"ชื่อบนหัวผิด" ซึ่งคนอ่านจับได้เอง

### ข. ชั่วโมงทศนิยมบนการ์ดอนุมัติ OT (คนละระบบกับงานนี้)

`app.js` ราวบรรทัด 16694 และ 16796 ประกอบสตริงเอง: `${t.hours} ชม.` และ `รวม ${group.totalHours} ชม.`
⇒ ใบที่เก็บ 3.5 หรือ 6.33 จะอ่านเป็นทศนิยมเหมือนกับที่เจ้าของทักมา

**ไม่แก้เพราะ:** มันคือการ์ดของ**ระบบอนุมัติ OT** ซึ่ง memory สั่งไว้ว่าต้องยืนยันกับเจ้าของก่อนลงมือ
([[feedback-attendance-confirm-before-build]] — มีหลายระบบชื่อคล้ายกัน) · รอบ 6 แก้เฉพาะจุดที่อยู่
**บนฟอร์มทำงานวันหยุดเดียวกัน** (การ์ดเทียบเงิน, คำเตือนใบ OT ซ้ำ) และรายการที่ถอน ซึ่งพิมพ์ชั่วโมง
ของเรคอร์ดวันหยุดโดยตรง

**ถ้าจะทำ:** ใช้ `holidayWorkDurationLabel(Math.round(h * 60)).hm` แบบเดียวกับที่รอบ 6 ใช้ และ
แก้ทั้งสาขา `ja` ด้วย (ตัวจัดรูปแบบมีสาขาของตัวเองอยู่แล้ว จึงไม่ต้องเพิ่มคีย์ใน `lang/ja.js`)

### ค. สามข้อที่รีวิวจัดเป็น "สงสัย" และผมไม่ยืนยัน

- `attendance/sw.js` อ้างว่าการล้างแคชเก่า "รันตอน activate ซึ่งคือตอนที่ `?v=` ใหม่โผล่" — แต่การบัมพ์
  `?v=` แก้ `index.html` ไม่ได้แก้ `sw.js` ⇒ worker ไม่ติดตั้งใหม่ `activate` ไม่ยิง · เป็นเรื่องแคช
  บวมช้าๆ ไม่ใช่เรื่องเงิน และผมไม่ได้ยืนยันพฤติกรรม install/activate ในเบราว์เซอร์จริง
- `server.js` รับ `sso.rate` เป็น 0 ได้ ขณะที่ทั้งสองเอนจินอ่าน `(S.sso.rate || 5) / 100` ⇒ ตั้ง 0%
  แล้วหัก 5% · ฝั่งเว็บปฏิเสธ 0 อยู่แล้ว จึงต้องยิง API ตรงๆ · **เป็นสูตรเงินของ SSO ไม่ใช่ของงานนี้**
  และการแก้ต้องรู้ว่าเจ้าของต้องการให้ตั้ง 0% ได้หรือไม่
- `Number(l.distanceKm || l.longDistanceKm) || 0` — ระยะ 0 กม. จะตกไปใช้ค่าอีกตัว · ผมไม่ได้พิสูจน์ว่า
  เรคอร์ด 0 กม. มีอยู่ได้จริง

  **พารามิเตอร์** เมื่อฟังก์ชันรับแบบ destructuring (`function f({ a, b })`) แล้วนับจบที่นั่น
  ⇒ คืนมาแค่บรรทัดลายเซ็น · ยามใดที่ assert ว่า "ไม่มีสิ่งนี้ในฟังก์ชันนั้น" จึงเขียวฟรี ·
  `tests/holiday-work-attendance-row.test.js` แก้ไว้แล้วตั้งแต่ 2026-10-08 และ
  `tests/holiday-work-upcountry-badge.test.js` แก้เมื่อ 2026-10-28
  · **รอบ 6 ไล่ครบทั้ง repo แล้ว และผลคือไม่มียามเปล่าอยู่จริงวันนี้**: 39 ไฟล์มีสำเนาของตัวตัดนี้
  และทุกไฟล์ที่ดึงฟังก์ชันซึ่งรับพารามิเตอร์แบบมีปีกกา ใช้เวอร์ชันที่ข้ามพารามิเตอร์แล้วทั้งหมด
  (`dry-run`, `impersonation`, `write-gate` สำหรับ `apiFetch` · `cancel-revoke` สำหรับ
  `findOtDuplicate` · สองไฟล์ของงานนี้สำหรับ `buildAttendancePrintView`) · `checkin-time-edit`
  มีสำเนาที่ยังบั๊กแต่เลี่ยงไปตัดด้วย anchor เอง และเขียนบอกไว้ว่าทำไม
  · **24 ไฟล์ที่ยังถือสำเนาบั๊กอยู่เป็นอันตรายแบบแฝง**: วันที่ใครเพิ่มพารามิเตอร์แบบ destructuring
  **หรือแม้แค่ `= {}` เป็นค่าตั้งต้น** (รูปแบบนี้ก็ติดกับดักเดียวกันและผมไม่ได้คิดถึงตอนรอบ 5)
  ให้ฟังก์ชันที่ไฟล์นั้นดึงอยู่ ยาม "ไม่มีสิ่งนี้ใน f" ของไฟล์นั้นจะเขียวฟรีโดยไม่มีสัญญาณ ·
  `generatePeriodDays` กับ `attendanceDayForUser` ใน `server.js` **มี `= {}` รออยู่แล้ว** และ
  `checkout-review-switch` · `day-pay-preview` · `holiday-work-detail-block` ·
  `holiday-work-ot-segments` ดึงจาก `SERVER_SRC` ⇒ กลุ่มนี้เสี่ยงที่สุด
- **การนับจุดเรียกต้องนับจากชื่อฟังก์ชันที่ถูกเรียก ไม่ใช่ชื่อตัวแปรที่รับผล** · จุดที่หลุดมาแล้วสองรอบ
  คือจุดที่ถูกเพิ่มทีหลังด้วยชื่อตัวแปรอื่น
- **เกณฑ์ `>= n` ในยามนับจำนวน คือรูที่ขนาดเท่ากับ `จำนวนจริง - n`** · ใช้ `=== n` แล้วตรึงชื่อ
  ของแต่ละจุดแยกกัน
- **ยามต้องพิสูจน์ว่ากัด** ไม่ใช่พิสูจน์ว่าเขียว · วิธีที่ใช้: โหลดซอร์สเข้าหน่วยความจำ ใส่ mutation
  ที่ย้อนการแก้ แล้วดูว่ายามแดง — ไม่แตะไฟล์จริง และเช็กท้ายสคริปต์ว่าไฟล์ไม่ถูกเปลี่ยน
