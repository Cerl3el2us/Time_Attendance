## 1. push อัตโนมัติรายงาน "สำเร็จ" ได้ ทั้งที่ไม่ได้ก๊อปอะไรขึ้นไปเลย — `sync-push-false-success`

- **คืออะไร:** `sync_if_dirty.ps1` เห็นว่า DIRTY ⇒ เรียก `sync_memory.ps1 push` · ถ้าไฟล์ที่เปลี่ยน
  **ทุกไฟล์** ชนกับสำเนาบน NAS ที่ใหม่กว่าหรือเท่ากัน (เคส 5 ของตัวตัดสินทีละไฟล์) ผลคือ
  `copied=0 conflict=n` แต่ `rc=0` ⇒ นับเป็น **push สำเร็จ** ⇒ **เขียนหมุด** ⇒ ตั้งแต่นั้นโฟลเดอร์
  อ่านว่า CLEAN ทุกเทิร์น
- **พังอย่างไรได้จริง:** เทิร์นนี้แก้ `MEMORY.md` ในเครื่อง แต่ NAS มีสำเนาที่ stamp ใหม่กว่า (เครื่องบ้าน
  push ทีหลัง หรือ clock skew) ⇒ hook บอกว่าเรียบร้อย, หมุดถูกเขียน, ไม่มีใครเห็นอะไรผิด · เปิด session
  ครั้งถัดไป **`pull` ทับไฟล์ในเครื่องด้วยฉบับที่เก่ากว่าของเรา** (มีสำเนาที่ `.sync_backup\` แต่ไม่มีใครรู้
  ว่าต้องไปหา) ⇒ งานที่เขียนในเทิร์นนั้นหายจากทั้งสองเครื่องอย่างเงียบๆ
- **ที่เดียวที่บันทึกไว้:** ฟิลด์ `needs-eyes=` ใน `Z:\claude_memory\sync.log` (พร้อม `copied=` / `conflict=`)
- **สิ่งที่หายไปตอนทำ automation:** ก่อนมี hook คำเตือนนี้ถูก**พิมพ์ให้คนที่เพิ่งพิมพ์ "จบงาน" อ่าน**
  คนนั้นอยู่หน้าจอและเห็นมัน ⇒ automation ไม่ได้สร้างกับดักใหม่ แต่ **เอาคนอ่านออกไป** เหลือบรรทัดใน log
  ที่ไม่มีใครเปิด
- **คนอ่านที่ออกแบบไว้แล้วแต่ยังไม่ได้สร้าง:** บล็อกสุขภาพการ sync = **ข้อ 8 ของสเปก**
  `docs/superpowers/specs/2026-10-12-faster-startup-and-cross-machine-state-design.md` (เนื้อหาของแผนที่ 3)
  ⇒ จนกว่าจะมีสิ่งนั้น **ห้ามเชื่อว่า "hook ไม่บ่น" = memory ถึงอีกเครื่องแล้ว** ให้เปิด `sync.log` ดู

## 2. ไฟล์ memory ที่ชื่อไม่เข้า `$Patterns` ให้ผล "สำเร็จปลอม" แบบเดียวกัน

- **คืออะไร:** `sync_if_dirty.ps1` ตัดสิน DIRTY จากเวลาแก้ไขของไฟล์ในโฟลเดอร์ แต่ `sync_memory.ps1`
  ก๊อปเฉพาะไฟล์ที่ชื่อเข้า `$Patterns` 4 แบบ ⇒ ไฟล์ที่ชื่อไม่เข้าทำให้ DIRTY ได้ แต่ไม่ถูกก๊อป
  ⇒ `copied=0`, `rc=0`, **หมุดถูกเขียน**, ไฟล์นั้นไม่เคยเดินทางไปไหนเลย
- **พังอย่างไรได้จริง:** เขียนบทเรียนใหม่ลง `lesson_*.md` หรือ `notes_*.md` ในโฟลเดอร์ memory
  ⇒ hook บอกว่า push สำเร็จ ⇒ อีกเครื่องไม่เคยได้ไฟล์นั้น และไม่มีอะไรบอกว่าหายไป
- **เป็นครั้งที่ 4 ของกับดักเดียวกัน** — `$Patterns` ทำคำสั่งของเจ้าของหลุดมาแล้วสามครั้งก่อนหน้า
  (ล่าสุดคือ `feedback_pending_task_format.md` ที่ต้องเขียนหมายเหตุกำกับใน `MEMORY.md` ว่าทำไมไม่มีสำเนา
  ในโฟลเดอร์โปรเจกต์ และ `session_handoff.md` ในข้อ 6 ด้านล่าง)
- **ยามที่ออกแบบไว้:** ข้อ 8 ของสเปกเดียวกัน (รายงานไฟล์ที่ dirty แต่ไม่ถูกก๊อป) — **ยังไม่ได้สร้าง**

## 3. `Stop` ให้เวลา 20 วิ แต่ push จริงที่วัดได้ใช้ 27.4 วิ — `sync-stop-timeout` — **ปิดแล้ว 2026-10-12**

> **ปิดแล้ว:** เจ้าของเลือกขึ้น `Stop` เป็น 60 วิ (เท่า `SessionEnd`) เมื่อ 2026-10-12 · ข้อความด้านล่างคือสภาพ
> **ก่อนแก้** เก็บไว้เป็นเหตุผล ไม่ใช่สถานะปัจจุบัน · บันทึกปิดอยู่ใน `docs/STATUS_CLOSED.md` ข้อ "hook `Stop`" ·
> ข้อความ "60 ซึ่งเป็นค่าสูงสุด" ด้านล่าง **ยังไม่เคยตรวจกับเอกสาร Claude Code**

- **ตัวเลข:** `Z:\.claude\settings.json` ตั้ง `Stop` timeout = **20** วิ (`SessionEnd` = 60 ซึ่งเป็นค่าสูงสุด)
  · ทางเดิน CLEAN วัดได้ 0.072–0.092 วิ (ไม่แตะ NAS เลย) · แต่ **ทางเดิน DIRTY ครั้งเดียวที่วัดได้จริง
  ใช้ 27.4 วิ** ⇒ เกินงบของ `Stop`
- **พังอย่างไรได้จริง:** บนลิงก์ที่ช้ากว่า LAN (VPN / Wi-Fi อ่อน) hook ถูกฆ่ากลางการก๊อปทุกเทิร์นที่มีไฟล์
  เปลี่ยน · **หมุดถูกกันไม่ให้เขียนอย่างถูกต้องแล้ว** (เขียนเมื่อ push สำเร็จเท่านั้น) ⇒ ไม่มีการโกหกว่า
  sync แล้ว **แต่ต้นทุนนั้นถูกจ่ายซ้ำทุกเทิร์น** โดยไม่มีเทิร์นไหนทำสำเร็จ จนกว่า `SessionEnd` (60 วิ)
  จะได้ทำงาน ⇒ **นี่คือข้อแลกเปลี่ยนที่เจ้าของตั้งเองว่า "ข้อจำกัดคือเวลา"** จึงไม่ใช่บั๊กที่แก้ได้ฝ่ายเดียว
  ต้องให้เจ้าของตัดสินว่าจะขึ้น timeout, ย้ายไป `SessionEnd` อย่างเดียว, หรือยอมให้ซ้ำ
- **ผลข้างเคียงที่แรงกว่า:** run ที่ถูกฆ่ากลางทางทิ้ง **`Z:\claude_memory\.git\index.lock`** ค้างไว้ได้
  ⇒ หลังจากนั้น **การ snapshot ทุกครั้งล้มเหลว** โดยมีร่องรอยเพียงบรรทัดเดียวใน`sync.log`
  (ฟิลด์ `snapshot=`) ⇒ ตาข่ายรอง git บน NAS หยุดทำงานเงียบๆ ทั้งที่ push ยังเขียนไฟล์ได้ตามปกติ
  · **วิธีตรวจ:** `ls "Z:\claude_memory\.git\index.lock"` — ถ้ามี ให้ลบเมื่อแน่ใจว่าไม่มี git ตัวไหนกำลังทำงาน

## 4. hook push โฟลเดอร์ `Z--` เสมอ ไม่สนใจว่า session เปิดจากที่ไหน

- **คืออะไร:** hook ส่ง `-ProjectDir "Z:\\"` แบบตรึงค่า ⇒ sanitize เป็น `Z--` ทุกครั้ง ไม่ว่าเซสชันนั้นจะเปิด
  อยู่ที่โฟลเดอร์ใด · ตรงกันข้ามกับ `session_start.ps1` ที่ **มียามสำหรับเคสนี้โดยเฉพาะ**
- **พังอย่างไรได้จริง:** เปิดเซสชันในโปรเจกต์อื่นบนเครื่องเดียวกัน แล้วแก้ไฟล์ memory ของโปรเจกต์นั้น
  ⇒ hook ไป push โฟลเดอร์ `Z--` (Time Attendance) แทน ⇒ ของโปรเจกต์นั้นไม่ขึ้น และรายงานว่าสำเร็จ
- **ทำไมยังปล่อยไว้:** ค่าตรึงนี้คือสิ่งที่กันกับดักที่แรงกว่า (พึ่ง `$PWD` เคยทำให้ push "สำเร็จ"
  พร้อมรายชื่อไฟล์ที่ดูน่าเชื่อ โดยข้ามทุกไฟล์ที่เซสชันนั้นเขียน — 2026-10-02) ⇒ **จงใจเลือกตรึง**
  แต่ต้องรู้ว่าอีกด้านของการตรึงคือข้อนี้
- **ประวัติที่เกี่ยวข้อง:** 2026-10-09 มีโฟลเดอร์ memory หลงยุค 4 โฟลเดอร์ใน `.claude/projects/`
  ที่เกิดจากกับดักตระกูลนี้ และถูกลบทิ้งไปแล้ว (มีบันทึกในสารบัญ "ปิดแล้ว")
